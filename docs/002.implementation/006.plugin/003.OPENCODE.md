# 003.OPENCODE.md

이 문서는 OpenCode Plugin의 구현 방안을 정합니다. [Plugin Specification](../../001.model/005.PLUGIN_SPEC.md#에이전트별-문서)이 정한 에이전트별 문서이며, Plugin의 역할과 규칙은 model 문서를 따릅니다. Plugin 공통 구현 방안은 [Plugin Guide](../004.PLUGIN_GUIDE.md)를, 용어는 [Glossary](../../001.model/002.GLOSSARY.md)를 따릅니다.

에이전트 id는 `opencode`입니다.

## 대상 버전

이 문서는 OpenCode 1.19.x를 대상으로 합니다. 아래 내용은 OpenCode 1.19.5가 기록한 DB와 v1.19.5 소스에서 확인했습니다. v1.19.0과 v1.19.5는 DB 마이그레이션 목록과 이벤트 정의가 같습니다. 그 사이 버전은 따로 확인하지 않았습니다.

2.x는 지원하지 않습니다. `event` 테이블의 이벤트 종류와 형식이 달라서, 2.x가 기록한 레코드는 모르는 레코드로 건너뜁니다.

## Session ID와 Agent ID

OpenCode는 Subagent를 띄울 때 Subagent만의 session(child session)을 새로 만듭니다. child session은 자신을 띄운 session의 id를 `parentID`로 기록합니다. 그래서 OpenCode에서는 Agent마다 session id가 다르며, Main Agent의 session id만 Session ID가 됩니다.

| Agent | Session ID | Agent ID | 부모 Agent ID |
|---|---|---|---|
| Main Agent | Main Agent의 session id | Session ID | 비움(NULL) |
| Subagent | Main Agent의 session id | Subagent의 session id | 자신을 띄운 Agent의 session id(`parentID`) |

### Session ID

session id와 `parentID`는 `session` 테이블의 `id`, `parent_id` 열과 `session.created.1` 이벤트의 `info`에 있습니다. `parentID`가 없는 session이 Main Agent의 session이며, 그 session id가 Session ID입니다. Subagent의 session에서는 `parentID`를 따라 `parentID`가 없는 session까지 올라가 Session ID를 찾습니다. Subagent의 session id는 Session ID가 아니므로 Transport Unit의 `session.id`에 넣지 않습니다([Plugin Specification](../../001.model/005.PLUGIN_SPEC.md#session-id와-agent-id) 참고).

### Agent ID

각 Agent의 session id를 Agent ID로 씁니다. Main Agent는 Agent ID와 Session ID가 같습니다.

### 부모 Agent ID

- **Main Agent**: `parentID`가 없으므로 비웁니다.
- **Subagent**: session의 `parentID`를 부모 Agent ID로 씁니다. Subagent가 띄운 Subagent라면 `parentID`는 부모 Subagent의 session id입니다.

## Trigger

Session Log 변경 감지를 Trigger로 씁니다. OpenCode에 아무것도 설치하거나 설정하지 않으며, 알림은 수집을 시작하라는 신호로만 씁니다. 무엇이 새로운지는 DB를 읽어 판단합니다.

| 시점 | 동작 |
|---|---|
| Plugin을 시작할 때 | 한 번 수집합니다. Daemon이 꺼져 있던 동안의 기록은 알림이 오지 않기 때문입니다. |
| DB 디렉터리의 변경 알림 | 파일 이름이 `<DB 파일 이름>-wal`이거나 없으면(`null`) 수집합니다. |
| 30초마다 | 수집합니다. 감시가 걸려 있지 않으면 다시 겁니다. |

- **감시 대상**: `fs.watch`로 DB 파일이 있는 디렉터리를 감시합니다. WAL 파일은 마지막 연결이 닫힐 때 삭제되므로 파일에 직접 걸지 않습니다.
- **거르는 알림**: `-shm` 파일은 읽기만 해도 바뀌므로 거릅니다. Plugin이 읽을 때 `-wal` 파일이 새로 만들어져 알림이 올 수 있지만, 다음 수집이 빈 조회로 끝납니다.
- **알림 횟수**: 커밋이 이어지면 알림이 하나로 합쳐집니다. 그래서 알림 횟수를 레코드 수로 쓰지 않고, 수집할 때마다 저장한 위치 이후를 읽습니다.
- **수집 중 알림**: 수집을 겹쳐 실행하지 않습니다. 수집 중에 알림이 오면 표시만 해 두고, 끝난 뒤 한 번 더 수집합니다.
- **30초 주기**: 큐가 넘치거나 감시가 멈추거나 파일시스템이 알림을 주지 않아 알림이 빠지는 경우에 대비합니다. OpenCode를 아직 실행하지 않아 디렉터리가 없을 때도 이 주기로 다시 시도합니다.
- **읽기 연결**: 읽기 전용 연결 하나를 Plugin이 멈출 때까지 유지합니다. 수집할 때마다 연결을 열고 닫으면 `-wal` 파일이 만들어지고 지워지며 알림이 이어질 수 있기 때문입니다. DB 파일이 다른 파일로 바뀌면 다시 엽니다.

Daemon이 꺼져 있는 동안 기록된 내용은 `event` 행이 남아 있는 한 다음 시작 때 수집합니다.

## Session Log

OpenCode는 Session Log를 SQLite DB 하나에 기록합니다. DB는 WAL 모드이며, 이벤트 로그인 `event` 테이블을 레코드로 씁니다. `message`, `part` 테이블은 행을 제자리에서 갱신하므로 수집에 쓰지 않습니다.

### 위치

| 조건 | 위치 |
|---|---|
| 기본(채널이 `latest`, `beta`, `prod`이거나 `OPENCODE_DISABLE_CHANNEL_DB`가 `1`, `true`) | `$XDG_DATA_HOME/opencode/opencode.db` |
| 그 밖의 채널 | `$XDG_DATA_HOME/opencode/opencode-<채널>.db` |
| `OPENCODE_DB` 환경 변수 | 그 값. 상대 경로는 `$XDG_DATA_HOME/opencode/` 기준입니다. `:memory:`이면 수집할 수 없습니다. |
| 설정 파일의 `[plugins.opencode] database` | 그 값. 상대 경로의 기준은 위와 같습니다. 환경 변수보다 먼저 씁니다. |

`$XDG_DATA_HOME`의 기본값은 `~/.local/share`입니다. Session이 많아도 DB는 하나이므로 Session마다 파일을 찾지 않습니다. Plugin은 OpenCode의 채널을 알 수 없으므로, 채널 DB를 수집하려면 설정의 `database`로 경로를 지정합니다. Daemon은 OpenCode와 다른 환경 변수로 실행될 수 있으므로 `OPENCODE_DB`는 Daemon에 설정된 값을 읽습니다.

### 레코드

레코드는 `event` 행 하나입니다.

| 열 | 설명 |
|---|---|
| `id` | 이벤트의 고유 id입니다. |
| `aggregate_id` | 이벤트를 기록한 session의 id입니다. Subagent의 session도 자신의 id로 기록됩니다. |
| `seq` | `aggregate_id` 안의 순번입니다. |
| `type` | `message.part.updated.1`처럼 버전이 붙은 이벤트 종류입니다. |
| `data` | 이벤트 내용을 담은 JSON입니다. |

OpenCode는 이벤트를 `event`, `event_sequence`, `message`, `part` 쓰기와 한 트랜잭션으로 커밋합니다. 그래서 읽을 수 있는 행은 항상 완전하며, 줄이 잘렸는지 판단할 필요가 없습니다.

### 수집 위치

수집 위치는 `aggregate_id`별 `seq`입니다. Plugin Guide의 파일 위치 대신 이 값을 저장하며, [Plugin Guide](../004.PLUGIN_GUIDE.md#session-log를-파일로-수집하는-경우)의 메모리 지침대로 진행 중인 Turn의 `turn.id`와 다음 Turn 안 위치도 함께 저장합니다. 저장하는 곳은 `stateDirectory`의 `positions.json`입니다. 임시 파일에 쓴 뒤 이름을 바꾸어 교체합니다.

저장하는 `seq`는 그 앞의 행을 모두 넘긴 위치입니다. 아직 끝나지 않은 message의 part는 [변환](#변환) 때문에 메모리에 있으므로, 그 message가 끝나기 전의 위치를 저장합니다. 다시 시작하면 그 위치부터 읽어 같은 Session Log Event를 만듭니다.

수집은 다음 순서로 진행합니다.

1. `event_sequence`에서 session마다 최신 `seq`를 읽어 저장한 위치와 비교합니다.
2. 바뀐 session마다 저장한 위치 다음부터 1번에서 읽은 `seq`까지 읽습니다. 이 상한이 한 번에 수집하는 범위이며, 그 뒤에 기록된 행은 다음 수집에서 읽습니다.

```sql
SELECT aggregate_id, seq FROM event_sequence;

SELECT id, seq, type, data FROM event
WHERE aggregate_id = ? AND seq > ? AND seq <= ?
ORDER BY seq
LIMIT ?;
```

- `LIMIT`으로 행을 나누어 읽어 읽기 트랜잭션을 짧게 유지합니다. 긴 읽기는 OpenCode의 기록을 막지는 않지만 checkpoint를 늦춥니다.
- `bun:sqlite`의 읽기 전용 연결로 읽습니다.

### Session Log가 바뀌었을 때

| 상황 | 처리 |
|---|---|
| 저장한 `aggregate_id`가 `event_sequence`에 없음 | session이 삭제된 것으로 보고 그 수집 위치를 지웁니다. |
| 저장한 `seq`가 `event_sequence`의 `seq`보다 큼 | 그 session을 처음부터 다시 수집합니다. event id가 같으므로 Main Server가 중복을 걸러냅니다. |
| `event` 테이블이 없음 | 로그를 남기고 수집하지 않습니다. 다음 주기에 다시 확인합니다. |

### 끝난 레코드 판단

OpenCode 1.19.x는 part 하나를 여러 행으로 기록하므로, 행이 완전해도 part는 끝나지 않았을 수 있습니다. 그래서 Trigger는 커밋마다 발동하고, 끝났는지는 수집 단계에서 part 종류별로 판단합니다.

| `message.part.updated.1`의 part | 기록 순서 | 변환하는 행 |
|---|---|---|
| `tool` | `state.status`가 `pending`, `running`, `completed` 또는 `error` | `completed`, `error` |
| assistant `text`, `reasoning` | `time.start`만 있음, `time.end` 있음 | `time.end`가 있는 행 |
| user `text` | `time` 없이 한 번 | 그 행 |
| `step-start`, `step-finish` | 한 번 | 그 행 |

끝나지 않은 상태의 행은 변환하지 않고 지나갑니다. 마지막 행이 part의 내용을 모두 담고 있으므로 이 행들을 다시 읽을 필요가 없습니다. 1.19.5의 DB에서 part 42개의 마지막 행이 `part` 테이블과 같은 것을 확인했습니다. `message.part.delta`는 DB에 기록되지 않습니다.

끝난 행만 변환하고 LLM Call은 message가 끝나야 만들 수 있으므로 다음 레코드는 곧바로 수집하지 못합니다.

- 오래 실행되는 tool은 그 message가 끝날 때까지 나타나지 않습니다. Subagent를 띄운 tool도 같습니다.
- OpenCode가 강제 종료되면 끝 표시가 없는 message는 같은 session의 다음 assistant message가 시작될 때 넘깁니다. 내용이 없으면 넘기지 않습니다. 다음 message가 없으면 넘기지 못합니다. 끝나지 않은 `text`와 `reasoning`은 내용이 DB에 없으므로 빠지고, 실행 중이던 tool은 `tool_use` 블록만 남습니다.

## 변환

[Plugin Specification](../../001.model/005.PLUGIN_SPEC.md#transport-unit)의 레코드는 OpenCode에서 message 하나입니다. Session Log Event는 message를 끝내는 `event` 행에서 만듭니다. OpenCode는 message 하나의 내용을 part별로 여러 행에 나누어 기록하는데, `assistant_message`는 LLM Call 하나의 내용을 한 번에 담아야 하기 때문입니다. 끝나지 않은 message의 part만 메모리에 둡니다. 쓰는 행은 `message.updated.1`, `message.part.updated.1`, `message.removed.1`, `message.part.removed.1`이며 `session.updated.1`은 쓰지 않습니다.

### message가 끝나는 때

| message | 끝나는 때 |
|---|---|
| assistant | `time.completed`가 기록되고 모든 `tool` part가 `completed`나 `error`일 때. subtask는 `time.completed`를 먼저 기록하고 tool 결과를 나중에 기록합니다. |
| user | part에 끝 표시가 없으므로, 다음 message가 시작될 때 끝난 것으로 봅니다. |

assistant message가 진행 중일 때 시작된 user message(대기열에 넣은 프롬프트)는 그 assistant message를 넘긴 뒤에 넘깁니다. 진행 중인 응답은 이 프롬프트를 보지 못했고, Turn의 끝을 판단하려면 먼저 넘겨야 하기 때문입니다. message id는 시간순이므로, 이미 넘긴 message의 id보다 작은 message의 갱신은 무시합니다. 넘긴 뒤 기록된 `summary`나 prune으로 인한 갱신이 여기에 해당합니다.

### user message

| user message | 변환 |
|---|---|
| synthetic이 아닌 part가 있음 | Turn을 시작하는 `user_message`입니다. |
| `compaction` part의 `auto`가 `false` | Turn을 시작하는 `user_message`입니다. OpenCode가 프롬프트를 기록하지 않으므로 `text`는 빈 문자열입니다. |
| `compaction` part의 `auto`가 `true` | 만들지 않습니다. `trigger`만 기억합니다. |
| 모든 part가 synthetic | `context_message`입니다. Turn을 시작하지 않습니다. compaction 뒤 이어 가라는 지시, subtask 결과를 요약하라는 지시가 여기에 해당합니다. |

`text`는 `text` part와 `subtask` part의 `prompt`를 잇습니다. `ignored` part는 모델에 들어가지 않으므로 뺍니다. `text/plain`이 아닌 `file` part는 `[Attached <mime>: <파일 이름>]`로 나타냅니다. 첨부 원본은 싣지 않습니다. `<message id>`가 `event_id`입니다.

overflow compaction 뒤 OpenCode가 synthetic 표시 없이 다시 넣는 원래 프롬프트는 다른 프롬프트와 구별할 수 없어 새 Turn이 됩니다. 앞 Turn은 다음 Turn이 시작된 것으로 끝납니다.

### assistant message

`step-start` part가 있거나 `tool` part가 없는 assistant message가 LLM Call입니다. 사용자 shell과 subtask는 `step-start` 없이 `tool` part만 기록합니다.

| Session Log Event의 필드 | 값 |
|---|---|
| `event_id` | message id |
| `timestamp` | `tool` part가 있으면 가장 이른 `state.time.start`, 없으면 `time.completed`. OpenCode는 도구를 응답 스트림 안에서 실행해 `time.completed`에 도구 실행 시간이 들어가기 때문입니다. |
| `started_at` | `time.created` |
| `model` | `modelID` |
| `content` | part 순서대로. `text`, `reasoning`은 끝난 내용이 빈 문자열이 아니면 넣습니다. provider가 reasoning을 암호화하면 `text`가 비어 있어 블록이 없습니다. `tool` part는 `tool_use` 블록이며 `tool_use_id`는 `callID`입니다. |
| `stop_reason` | `finish`가 `stop`이면 `end_turn`, `tool-calls`이면 `tool_use`, `length`이면 `max_tokens`, `content-filter`이면 `refusal`, 그 밖의 값이면 `other`입니다. `finish`가 없으면 뺍니다. |
| `usage` | `step-finish` part의 `tokens`입니다. `input`은 cache와 reasoning을 뺀 값이고, 기록된 `0`은 그대로 넣습니다. `step-finish`가 없으면 뺍니다. |
| `attempt` | 뺍니다. 아래를 참고하세요. |

`tool` part마다 같은 Transport Unit에 `tool_result`를 넣습니다. `event_id`는 `<message id>:<callID>`, `timestamp`는 `state.time.end`, `output`은 `state.output`이나 `state.error`, `is_error`는 `state.status`가 `error`인지입니다. `task` tool의 `state.metadata.sessionId`가 `subagent_id`입니다.

### 오류와 중단

message의 `error.name`으로 나눕니다.

| `error.name` | 변환 |
|---|---|
| `MessageAbortedError` | 사용자 중단입니다. 받은 내용이 있으면 `assistant_message`와 `tool_result`를 넘기고(`stop_reason`과 `usage` 없음), 그 뒤에 `turn_interrupted`를 넘깁니다. `event_id`는 `<message id>:interrupted`입니다. |
| `MessageOutputLengthError` | 오류가 아니라 `stop_reason`의 `max_tokens`입니다. |
| 그 밖의 값 | `error`가 있는 `assistant_message`입니다. `code`는 `error.name`, `message`는 `error.data.message`, `status_code`는 `error.data.statusCode`입니다. |

OpenCode는 재시도할 수 있는 오류를 message에 기록하지 않고 같은 message 안에서 다시 요청합니다. 재시도 상태는 메모리의 session status에만 있습니다. 그래서 message에 남은 오류는 다시 시도하지 않는 오류이므로 `will_retry`는 항상 `false`이고, 실패한 시도는 LLM Call로 보이지 않으며, `attempt`를 알 수 없습니다.

`content-filter`로 끝난 응답은 OpenCode가 message를 끝낸 뒤 오류를 더하지만, 이미 `stop_reason`의 `refusal`로 넘긴 뒤입니다. 구조화 출력을 받지 못한 `StructuredOutputError`도 같은 시점에 더해지므로 나타나지 않습니다.

### Turn 단위

| [끝나는 방식](../../001.model/005.PLUGIN_SPEC.md#turn-단위) | OpenCode에서 알아보는 방법 |
|---|---|
| 최종 응답 | `error`와 `tool` part가 없고 `finish`가 `tool-calls`, `unknown`이 아닌 값입니다. OpenCode가 Loop를 멈추는 조건과 같습니다. |
| LLM 호출 오류로 멈춤 | `error`가 있는 assistant message |
| 요청한 compaction 완료 | `auto`가 `false`인 compaction의 요약 |
| 사용자 중단 | `MessageAbortedError` |
| 다음 Turn 시작 | 위 [user message](#user-message)의 Turn을 시작하는 message |

### compaction

`summary`가 `true`인 assistant message가 요약입니다. compaction의 시작은 따로 기록되지 않으므로, 이 message 하나에서 `compaction`(`event_id`는 `<message id>:compaction`, `timestamp`는 `time.created`)과 `compaction_summary`(`<message id>:summary`, `time.completed`)를 차례로 만듭니다. `context_tokens_before`는 기록되지 않아 뺍니다. 요약이 실패하면 `compaction_summary` 대신 `error`가 있는 `assistant_message`를, 중단되면 `turn_interrupted`를 넣습니다.

compaction 앞에서 컨텍스트 초과로 응답을 받지 못한 message에는 `error`도 `finish`도 없습니다. 내용이 빈 `assistant_message`로 넘어갑니다.

### LLM Call 없는 도구 실행

사용자 shell과 subtask의 message는 `context_message`로 넘깁니다. `event_id`는 message id이고, `text`는 도구 이름, 인자, 결과를 이은 것입니다. Tool Call은 LLM Call이 요청한 것이어야 하므로 Tool Call로 나타내지 않습니다.

사용자 shell은 Turn이 끝난 뒤에 실행되며 그 자체로는 Turn을 끝낼 응답이 없습니다. 그래서 다음 프롬프트까지 기다렸다가 그 Turn의 `user_message` 바로 뒤에 넘깁니다. 다음 프롬프트가 없으면 넘기지 않습니다. 뒤 LLM Call의 input에는 이 결과가 들어가므로, 이렇게 하면 shell만으로 Turn이 `errored`로 보이지 않으면서 input은 빠지지 않습니다.

## input 기록 범위

| input | 기록 | 나타나는 곳 |
|---|---|---|
| 사용자 메시지, 첨부의 이름 | O | `user_message` |
| 이전 모델 응답, 도구 결과 | O | `assistant_message`, `tool_result` |
| Skill | 일부 | Skill을 도구로 불러 읽은 내용은 `tool_result`에 있습니다. 시스템 프롬프트에 넣은 Skill 목록은 기록되지 않습니다. |
| Subagent에 넘긴 프롬프트 | O | Subagent의 `user_message` |
| compaction 결과 | O | `compaction_summary` |
| 에이전트가 넣은 지시문 | O | `context_message` |
| 시스템 프롬프트, AGENTS.md 같은 지침 파일, 도구 정의 | X | OpenCode가 DB에 기록하지 않으므로 보내지 않습니다. |
| 메모리에서 조합되어 요청에만 들어가는 reminder | X | 같습니다. |
| 첨부 파일의 내용 | X | `file` part에 있지만 싣지 않습니다. |

다음은 기록된 내용과 모델이 실제로 받은 input이 다를 수 있는 경우입니다.

- **compaction의 tail**: OpenCode는 compaction 뒤에도 최근 Turn 일부를 요약하지 않고 남길 수 있습니다(`tail_start_id`). [LLM Call의 input](../../001.model/003.domain_model/008.LLM_CALL.md#구성-규칙)은 `compaction`에서 시작하므로 이 부분이 보이지 않습니다.
- **prune**: OpenCode가 오래된 도구 결과를 지워도(`time.compacted`) 넘긴 `tool_result`는 그대로입니다.
- **오류로 끝난 응답**: OpenCode는 오류로 끝난 message를 다음 요청에 넣지 않지만, 뒤 LLM Call의 input에는 나타납니다([LLM Call](../../001.model/003.domain_model/008.LLM_CALL.md#결정되지-않은-사항) 참고).

제목과 message 요약을 만드는 LLM 호출은 message를 만들지 않으므로 LLM Call로도, Token Usage로도 나타나지 않습니다.

## 결정되지 않은 사항

- 오래 실행되는 tool을 끝나기 전에 보여 줄지
- Bun의 `fs.watch`가 macOS에서 위 Trigger대로 동작하는지. Linux의 Bun 1.4.4에서는 다른 연결의 커밋으로 Trigger가 발동하는 것을 시험했습니다. 실제 OpenCode가 쓰는 중에는 시험하지 않았습니다.
- 실제 기록으로 확인하지 않은 변환. 1.19.5의 DB에는 정상 종료한 Turn만 있어서, Subagent, compaction, 오류, 중단, 사용자 shell, subtask는 v1.19.5 소스에서 읽은 기록 순서로 만든 테스트로만 확인했습니다.
- 부모 session을 찾을 수 없어 Session ID를 정하지 못할 때의 처리. 지금은 로그를 한 번 남기고, 수집 위치를 옮기지 않은 채 다음 수집에서 다시 시도합니다.
- overflow compaction 뒤 다시 넣은 프롬프트를 원래 Turn에 이어 붙일지
