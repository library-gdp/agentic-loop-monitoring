# 001.OVERVIEW.md

이 문서는 OpenCode v1(1.19.x) Plugin의 구현 방안을 정합니다. [Plugin Specification](../../../001.model/005.PLUGIN_SPEC.md#에이전트별-문서)이 정한 에이전트별 문서이며, Plugin의 역할과 규칙은 model 문서를 따릅니다. Plugin 공통 구현 방안은 [Plugin Guide](../../004.PLUGIN_GUIDE.md)를, 용어는 [Glossary](../../../001.model/002.GLOSSARY.md)를 따릅니다.

에이전트 id는 `opencode`입니다.

## 대상 버전

이 문서는 OpenCode 1.19.x를 대상으로 합니다. 아래 내용은 OpenCode 1.19.5가 기록한 DB와 v1.19.5 소스에서 확인했습니다. v1.19.0과 v1.19.5는 DB 마이그레이션 목록과 이벤트 정의가 같습니다. 그 사이 버전은 따로 확인하지 않았습니다.

2.x는 지원하지 않습니다. `event` 테이블의 이벤트 종류와 형식이 달라서, 2.x가 기록한 레코드는 모르는 레코드로 건너뜁니다.

## Session ID와 Agent ID

OpenCode는 Subagent를 띄울 때 Subagent만의 session(child session)을 새로 만듭니다. child session은 자신을 띄운 session의 id를 `parentID`로 기록합니다. 그래서 OpenCode에서는 Agent마다 session id가 다르며, Main Agent의 session id만 Session ID가 됩니다.

| Agent | Session ID | Agent ID | 부모 Agent ID |
|---|---|---|---|
| Main Agent | Main Agent의 session id | Session ID | 비움(NULL) |
| Subagent | Main Agent의 session id | Subagent의 session id | 자신을 띄운 Agent의 session id(`parentID`) |

### Session ID

session id와 `parentID`는 `session` 테이블의 `id`, `parent_id` 열과 `session.created.1` 이벤트의 `info`에 있습니다. `parentID`가 없는 session이 Main Agent의 session이며, 그 session id가 Session ID입니다. Subagent의 session에서는 `parentID`를 따라 `parentID`가 없는 session까지 올라가 Session ID를 찾습니다. Subagent의 session id는 Session ID가 아니므로 Transport Unit의 `session.id`에 넣지 않습니다([Plugin Specification](../../../001.model/005.PLUGIN_SPEC.md#session-id와-agent-id) 참고).

### Agent ID

각 Agent의 session id를 Agent ID로 씁니다. Main Agent는 Agent ID와 Session ID가 같습니다.

### 부모 Agent ID

- **Main Agent**: `parentID`가 없으므로 비웁니다.
- **Subagent**: session의 `parentID`를 부모 Agent ID로 씁니다. Subagent가 띄운 Subagent라면 `parentID`는 부모 Subagent의 session id입니다.

## Trigger

Session Log 변경 감지를 Trigger로 씁니다. OpenCode에 아무것도 설치하거나 설정하지 않으며, 알림은 수집을 시작하라는 신호로만 씁니다. 무엇이 새로운지는 DB를 읽어 판단합니다.

| 시점 | 동작 |
|---|---|
| Plugin을 시작할 때 | 한 번 수집합니다. Daemon이 꺼져 있던 동안의 기록은 알림이 오지 않기 때문입니다. |
| DB 디렉터리의 변경 알림 | 파일 이름이 `<DB 파일 이름>-wal`이거나 없으면(`null`) 수집합니다. |
| 30초마다 | 수집합니다. 감시가 걸려 있지 않으면 다시 겁니다. |

`-wal`, `-shm` 파일의 동작은 [OpenCode v1 WAL과 SHM](../../../003.reference/001.OPENCODE_WAL_AND_SHM.md)을 참고하세요.

- **감시 대상**: `fs.watch`로 DB 파일이 있는 디렉터리를 감시합니다. WAL 파일은 마지막 연결이 닫힐 때 삭제되므로 파일에 직접 걸지 않습니다.
- **거르는 알림**: `-shm` 파일은 읽기만 해도 바뀌므로 거릅니다. Plugin이 읽을 때 `-wal` 파일이 새로 만들어져 알림이 올 수 있지만, 다음 수집이 빈 조회로 끝납니다.
- **알림 횟수**: 커밋이 이어지면 알림이 하나로 합쳐집니다. 그래서 알림 횟수를 레코드 수로 쓰지 않고, 수집할 때마다 저장한 위치 이후를 읽습니다.
- **수집 중 알림**: 수집을 겹쳐 실행하지 않습니다. 수집 중에 알림이 오면 표시만 해 두고, 끝난 뒤 한 번 더 수집합니다.
- **30초 주기**: 큐가 넘치거나 감시가 멈추거나 파일시스템이 알림을 주지 않아 알림이 빠지는 경우에 대비합니다. OpenCode를 아직 실행하지 않아 디렉터리가 없을 때도 이 주기로 다시 시도합니다.

Daemon이 꺼져 있는 동안 기록된 내용은 `event` 행이 남아 있는 한 다음 시작 때 수집합니다.

## Session Log

OpenCode는 Session Log를 SQLite DB 하나에 기록합니다. DB는 WAL 모드이며, 이벤트 로그인 `event` 테이블을 레코드로 씁니다. `message`, `part` 테이블은 행을 제자리에서 갱신하므로 수집에 쓰지 않습니다.

### 위치

Plugin은 `AGENTOSCOPE_OPENCODE_DB`로 받은 DB 파일 하나를 수집하며, 값이 없으면 `<홈 디렉터리>/.local/share/opencode/opencode.db`를 씁니다. OpenCode가 쓰는 환경 변수와 설정은 읽지 않습니다. 자세한 내용은 [OpenCode v1 Plugin 설정](002.CONFIGURATION.md)을 참고하세요.

Session이 많아도 DB는 하나이므로 Session마다 파일을 찾지 않습니다.

### 레코드

레코드는 `event` 행 하나입니다.

| 열 | 설명 |
|---|---|
| `id` | 이벤트의 고유 id입니다. |
| `aggregate_id` | 이벤트를 기록한 session의 id입니다. Subagent의 session도 자신의 id로 기록됩니다. |
| `seq` | `aggregate_id` 안의 순번입니다. |
| `type` | `message.part.updated.1`처럼 버전이 붙은 이벤트 종류입니다. |
| `data` | 이벤트 내용을 담은 JSON입니다. |

OpenCode는 이벤트를 `event`, `event_sequence`, `message`, `part` 쓰기와 한 트랜잭션으로 커밋합니다. 그래서 읽을 수 있는 행은 항상 완전하며, 줄이 잘렸는지 판단할 필요가 없습니다.

### 수집 위치

수집 위치는 `aggregate_id`별 마지막 `seq`입니다. Plugin Guide의 파일 위치 대신 이 값을 저장하며, [Plugin Guide](../../004.PLUGIN_GUIDE.md#session-log를-파일로-수집하는-경우)의 메모리 지침대로 진행 중인 Turn의 `turn.id`와 다음 Turn 안 위치도 함께 저장합니다.

수집 위치와 [변환](#변환)에 필요한 상태는 [`PluginContext`의 `stateDirectory`](../../005.PLUGIN_INTERFACE.md#statedirectory)의 `state.json`에 session마다 저장합니다. `event` 행을 한 번에 읽은 만큼 변환할 때마다 저장합니다.

| 값 | 설명 |
|---|---|
| `seq` | 마지막으로 수집한 `seq`입니다. |
| 최근 Turn | 최근 Turn 4개의 `turn.id`, 다음 Turn 안 위치, 그 Turn에 속한 user message의 id입니다. 응답 도중 사용자가 다음 입력을 보내면 앞 Turn의 레코드가 다음 Turn이 시작된 뒤에 기록되므로, 지금 Turn 하나보다 많이 기억합니다. |
| 지금 assistant message와 step | assistant message의 id, `parentID`, 모델 이름, `time.created`, `summary`와, 열려 있는 step의 `step-start` 행의 `seq`입니다. |
| 최근 message id | 최근에 본 user message, Turn을 시작하지 않는 user message, 이미 변환한 assistant message의 id입니다. 종류마다 16개까지 기억합니다. |

`state.json`이 수집하는 DB와 다른 경로의 것이거나, 읽을 수 없거나, 형식이 맞지 않으면 버리고 처음부터 수집합니다.

수집은 다음 순서로 진행합니다.

1. `event_sequence`에서 session마다 최신 `seq`를 읽어 저장한 위치와 비교합니다.
2. 바뀐 session마다 저장한 위치 다음부터 1번에서 읽은 `seq`까지 읽습니다. 이 상한이 한 번에 수집하는 범위이며, 그 뒤에 기록된 행은 다음 수집에서 읽습니다.

```sql
SELECT aggregate_id, seq FROM event_sequence;

SELECT id, seq, type, data FROM event
WHERE aggregate_id = ? AND seq > ? AND seq <= ?
ORDER BY seq
LIMIT ?;
```

- `LIMIT`으로 행을 나누어 읽어 읽기 트랜잭션을 짧게 유지합니다. 긴 읽기는 OpenCode의 기록을 막지는 않지만 checkpoint를 늦춥니다.
- `bun:sqlite`의 읽기 전용 연결로 읽습니다.

### Session Log가 바뀌었을 때

| 상황 | 처리 |
|---|---|
| 저장한 `aggregate_id`가 `event_sequence`에 없음 | session이 삭제된 것으로 보고 그 수집 위치를 지웁니다. |
| 저장한 `seq`가 `event_sequence`의 `seq`보다 큼 | 그 session을 처음부터 다시 수집합니다. event id가 같으므로 Main Server가 중복을 걸러냅니다. |
| `event` 테이블이 없음 | 로그를 남기고 수집하지 않습니다. 다음 주기에 다시 확인합니다. |
| DB 파일이 없음 | 로그를 남기고 수집하지 않습니다. 다음 주기에 다시 확인합니다. |
| DB 파일이 다른 파일로 바뀜(inode가 다름) | 연결을 닫고 새 파일을 엽니다. |
| session이나 그 부모 session의 `session` 행이 없음 | Session ID를 정할 수 없으므로 그 session의 수집 위치를 옮기지 않고, 다음 수집에서 다시 시도합니다. |

### 끝난 레코드 판단

OpenCode 1.19.x는 part 하나를 여러 행으로 기록하므로, 행이 완전해도 part는 끝나지 않았을 수 있습니다. 그래서 Trigger는 커밋마다 발동하고, 끝났는지는 수집 단계에서 판단합니다.

| `message.part.updated.1`의 part | 기록 순서 | 끝난 행 |
|---|---|---|
| `tool` | `state.status`가 `pending`, `running`, `completed` 또는 `error` | `completed`, `error` |
| assistant `text`, `reasoning` | `time.start`만 있음, `time.end` 있음 | `time.end`가 있는 행 |
| user `text` | `time` 없이 한 번 | 그 행 |
| `step-start`, `step-finish` | 한 번 | 그 행 |

assistant message의 part는 하나씩 넘기지 않고, LLM 호출 한 번(step)이 끝난 `step-finish` 행에서 그 step의 part를 모아 변환합니다([LLM Call](#llm-call) 참고). 이때 `event` 테이블에서 그 step의 행을 다시 읽어 part마다 마지막 행을 씁니다. 마지막 행이 part의 내용을 모두 담고 있습니다. 1.19.5의 DB에서 part 42개의 마지막 행이 `part` 테이블과 같은 것을 확인했습니다. `message.part.delta`는 DB에 기록되지 않습니다.

`event` 행은 지우거나 바꾸지 않으므로(session을 지울 때만 함께 지워집니다), 다시 읽어도 같은 내용이며 변환은 결정적입니다. 행을 메모리에 모아 두지 않으므로 Daemon을 다시 시작해도 step의 시작부터 다시 읽어 이어 변환합니다.

그래서 다음 레코드는 곧바로 수집하지 못합니다.

- 모델의 응답은 step이 끝난 뒤 함께 넘어갑니다. 응답을 받는 동안에는 나타나지 않습니다.
- tool의 호출과 결과는 그 step의 tool이 모두 끝난 뒤 함께 넘어갑니다. 오래 실행되는 tool(Subagent를 띄운 `task` 등)은 끝날 때까지 나타나지 않습니다.
- 강제 종료로 `step-finish`도 오류 기록도 없이 남은 step은 넘기지 못합니다. 실제로 이런 step이 남는지는 확인하지 못했습니다.

## 변환

`event` 행 하나가 레코드 하나이며, 행 하나에서 나온 Session Log Event를 Transport Unit 하나로 넘깁니다. 변환에 쓰는 행은 `message.updated.1`과 `message.part.updated.1`뿐입니다.

### event id와 시각

- event id는 레코드인 `event` 행의 `id`(`evt_…`)입니다. 행 하나에서 Session Log Event가 여러 개 나오면 `<id>:<순번>`입니다. `evt_…`는 DB 전체에서 고유하므로 Agent ID를 붙이지 않습니다.
- `timestamp`는 `message.part.updated.1`이면 그 행의 `time`, `message.updated.1`이면 assistant message의 `time.completed`(없으면 `time.created`)입니다. OpenCode는 Unix epoch 밀리초로 기록하므로 RFC 3339(UTC)로 바꿉니다.

### Turn

| 레코드 | Session Log Event |
|---|---|
| user message에서 처음 기록된, `synthetic`도 `ignored`도 아닌 `text` part | Turn을 시작하는 `user_message`. `text`는 part의 `text`입니다. |
| user message의 `compaction` part(`auto`가 `false`) | Turn을 시작하는 `user_message`와 `compaction`(`trigger`: `manual`). 요청에 글이 없으므로 `text`는 빈 문자열이며, `turn.id`는 `<id>:0`입니다. |

- assistant message는 `parentID`가 가리키는 user message의 Turn에 넣습니다. Turn을 시작하지 않은 user message에 답하는 assistant message는 넘기지 않습니다.
- 첨부 파일이 있는 입력에서는 `file` part와 synthetic `text` part가 사용자가 입력한 `text` part보다 먼저 기록될 수 있으므로, 이런 part만으로는 Turn을 정하지 않고 다음 part를 기다립니다.
- `subtask` part로 시작하는 user message(subtask로 실행한 command)와 synthetic `text` part만 있는 user message(사용자의 shell 명령)는 Turn을 시작하지 않습니다.
- user message를 다시 기록한 행(`summary.diffs` 갱신)은 변환하지 않습니다.
- Subagent의 child session에서는 task의 `prompt`로 기록한 user message가 Turn을 시작합니다.

### LLM Call

step 하나(`step-start` part부터 `step-finish` part까지)가 LLM 호출 한 번이며, `step-finish` 행에서 `assistant_message` 하나와, 그 step에서 끝난 tool마다 `tool_result` 하나를 이 순서로 만듭니다. 응답 도중 오류로 OpenCode가 같은 assistant message에서 다시 시도해 `step-start`가 여러 번 기록되면, 마지막 `step-start` 뒤의 part만 씁니다.

| `assistant_message` 필드 | 값 |
|---|---|
| `model` | assistant message의 `modelID` |
| `content` | step의 part를 처음 기록한 순서대로: 글이 있는 `text`는 `text`, 글이 있는 `reasoning`은 `reasoning`, `tool`은 `tool_use`(`tool_use_id`: `callID`, `name`: `tool`, `input`: `state.input`). 공급자가 추론을 암호화해 넘긴 `reasoning` part는 글이 비어 있으므로 넣지 않습니다. |
| `stop_reason` | `step-finish`의 `reason`. 아래 표를 참고하세요. |
| `usage` | `step-finish`의 `tokens`. 아래 표를 참고하세요. |
| `started_at` | assistant message의 `time.created` |
| `timestamp` | `step-finish` 행의 `time` |

| `reason` | `stop_reason` |
|---|---|
| `stop` | `end_turn` |
| `tool-calls` | `tool_use` |
| `length` | `max_tokens` |
| `content-filter` | `refusal` |
| 그 밖의 값 | `other` |

| `tokens` | Token Usage |
|---|---|
| `input` | `input_tokens`. OpenCode는 cache로 읽고 쓴 토큰을 뺀 값을 기록합니다. |
| `output` | `output_tokens`. OpenCode는 reasoning 토큰을 뺀 값을 기록합니다. |
| `reasoning` | `reasoning_tokens` |
| `cache.read` | `cache_read_tokens` |
| `cache.write` | `cache_write_tokens` |

OpenCode는 공급자가 넘기지 않은 항목도 `0`으로 기록하므로, 기록된 `0`과 기록되지 않은 값을 구별할 수 없습니다. 기록된 값을 그대로 넣습니다.

`tool_result`는 마지막 행의 `state.status`가 `completed`나 `error`인 `tool` part마다 하나씩, `content`의 `tool_use` 순서로 만듭니다.

| `tool_result` 필드 | 값 |
|---|---|
| `tool_use_id` | `callID` |
| `output` | `completed`이면 `state.output`, `error`이면 `state.error` |
| `is_error` | `state.status`가 `error`이면 `true`, `completed`이면 `false` |
| `subagent_id` | `task` tool이면 `state.metadata.sessionId`(child session id, 곧 Subagent의 Agent ID) |
| `timestamp` | `state.time.end` |

### 오류와 중단

assistant message에 `error`가 처음 채워진 `message.updated.1` 행에서 변환합니다. 열려 있는 step이 있으면 그 step의 part를 위와 같이 `content`와 `tool_result`로 넣습니다. 같은 message를 다시 기록한 행은 변환하지 않습니다.

| `error.name` | Session Log Event |
|---|---|
| `MessageAbortedError`(사용자 중단) | `content`가 있으면 `stop_reason` 없는 `assistant_message`와 `tool_result`, 그 뒤에 `turn_interrupted`. 중단할 때 OpenCode는 실행 중인 tool을 `error` 상태로 기록합니다. |
| `MessageOutputLengthError` | `stop_reason`이 `max_tokens`인 `assistant_message`. 그 step을 이미 `step-finish`로 넘겼으면 넘기지 않습니다. |
| 그 밖의 값 | `error`가 있는 `assistant_message`. `message`는 `error.data.message`(없으면 `error.name`), `code`는 `error.name`, `status_code`는 `error.data.statusCode`, `will_retry`는 `false`입니다. |

- OpenCode는 다시 시도하는 오류를 DB에 기록하지 않고(재시도 상태는 `session.status`로 알리기만 합니다), message에 `error`를 채우면 루프를 멈춥니다. 그래서 기록된 오류는 모두 `will_retry`가 `false`이고, 실패한 시도는 넘기지 못하며 `attempt`도 넣지 않습니다.

### Compaction

| 레코드 | Session Log Event |
|---|---|
| user message의 `compaction` part(`auto`가 `true`) | 지금 Turn의 `compaction`(`trigger`: `auto`) |
| `summary`가 `true`인 assistant message의 `step-finish` | `compaction_summary`. `text`는 `text` part의 글을 빈 줄로 이어 붙인 것이고, `model`, `usage`는 [LLM Call](#llm-call)과 같습니다. |

- 자동 compaction은 Turn 도중에 일어나므로 Turn을 시작하지 않습니다. 그 뒤에 OpenCode가 기록하는 user message 하나(작업을 이어 가라는 synthetic `text`, 또는 요청이 한도를 넘었을 때 다시 기록한 마지막 사용자 입력)도 같은 Turn에 넣고 Turn을 시작하지 않습니다. 요약이 오류로 끝나면 이 처리를 하지 않습니다.
- `context_tokens_before`는 OpenCode가 기록하지 않으므로 넣지 않습니다.
- `tail_start_id`를 채워 다시 기록한 `compaction` part와, prune이 `state.time.compacted`를 채워 다시 기록한 `tool` part는 변환하지 않습니다.

### 쓰지 않는 레코드

| 레코드 | 이유 |
|---|---|
| `session.created.1`, `session.updated.1`, `session.deleted.1` | 작업 디렉터리와 부모 session은 `session` 테이블에서 읽습니다. |
| `message.removed.1`, `message.part.removed.1` | 되돌리기로 지운 message도 에이전트가 실제로 실행한 것이므로, 이미 넘긴 Session Log Event를 그대로 둡니다. |
| `step-start`, `step-finish` 밖의 assistant part 행, `patch` part | `step-finish`에서 그 step의 part를 다시 읽어 씁니다. |
| 모르는 `type`의 행(2.x의 이벤트 등) | 무시합니다. |

필요한 필드가 없거나 형식이 다른 `message.updated.1`, `message.part.updated.1` 행은 로그(`warn`)를 남기고 건너뜁니다.

## input 기록 범위

LLM Call의 input([Glossary](../../../001.model/002.GLOSSARY.md)) 가운데 넘기는 것과 넘기지 않는 것입니다.

| input | 넘기는지 | 설명 |
|---|---|---|
| 사용자 메시지 | O | 사용자가 입력한 `text` part |
| Subagent에 넘긴 프롬프트 | O | child session의 user message, 부모의 `task` tool 호출의 `input` |
| 이전 모델 응답 | O | `text`, 글이 있는 `reasoning`, tool 호출 |
| 도구 결과 | O | `tool` part의 `state.output`, `state.error`. prune한 출력도 원래 출력을 넘깁니다. 실제 input에서는 `[Old tool result content cleared]`로 바뀝니다. |
| compaction 결과 | O | 요약 assistant message의 `text` part |
| 시스템 프롬프트, 지침 파일, Skill, 도구 정의 | X | DB에 기록되지 않습니다. |
| 첨부 파일과 그 내용, `@이름`으로 부른 agent 안내 | X | `file`, `agent` part와 synthetic `text` part로 DB에 있지만, 이를 담을 Session Log Event가 없습니다. |
| 사용자의 shell 명령과 그 결과, subtask로 실행한 command | X | LLM 호출이 아니며 이를 담을 Session Log Event가 없습니다. |
| 자동 compaction 뒤 이어 가라는 글, 다시 기록한 마지막 사용자 입력 | X | Turn을 시작하지 않도록 넘기지 않습니다. |
| 암호화된 reasoning | X | 글이 없습니다. |
| 재시도로 실패한 시도, compaction 요약 호출의 input, 제목을 만드는 LLM 호출 | X | DB에 기록되지 않습니다. |

## 결정되지 않은 사항

- 끝 표시 없이 남은 part를 넘길지, 오래 실행되는 tool을 끝나기 전에 보여 줄지
- 첨부 파일 내용, 사용자의 shell 명령, subtask command를 Session Log Event로 넘기는 방법. Session Log Event 종류를 더해야 합니다.
- 권한 요청을 거절해 멈춘 Turn을 알아보는 방법. 지금은 다음 Turn이 시작될 때까지 진행 중인 Turn으로 남습니다.
- Bun의 `fs.watch`가 위 Trigger대로 동작하는지. Linux에서 Bun 1.4.4와 테스트용 WAL DB로 `-wal` 변경 알림을 확인했으며, 실제 OpenCode, macOS에서는 시험하지 않았습니다.
- child session의 `parent_id` 기록. 1.19.5의 소스로만 확인했으며, child session이 있는 DB로는 확인하지 못했습니다. 변환과 Subagent 연결은 그 소스대로 만든 테스트용 DB로 확인했습니다.
- 오류(`error.name`)의 종류. 확인한 DB에는 오류로 끝난 assistant message가 없어, 이름은 1.19.5의 소스를 따랐습니다.
