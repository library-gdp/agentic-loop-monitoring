# 008.DATA_STORAGE.md

이 문서는 [Data Architecture](../001.model/008.DATA_ARCHITECTURE.md)가 정한 Main Server의 데이터를 저장하는 방안을 정합니다. 데이터의 구분과 쓰기, 읽기 규칙은 model 문서를 따르며, 이 문서는 바꾸지 않습니다. 이 문서의 내용은 Main Server의 Persistence 모듈이 구현합니다([Application Architecture](../001.model/007.APPLICATION_ARCHITECTURE.md#persistence) 참고). 용어는 [Glossary](../001.model/002.GLOSSARY.md)를 따릅니다.

## 저장소

Main Server의 데이터를 SQLite 데이터베이스 파일 하나에 저장합니다. 결정 배경은 [Store Main Server data in SQLite](../../adr/2026-10-28-store-main-server-data-in-sqlite.md)를 참고하세요.

SQLite에는 Bun에 내장된 `bun:sqlite`로 접근합니다. 동기 API이므로 쓰기 트랜잭션과 질의가 도는 동안 같은 프로세스의 Daemon과 Visualization이 기다립니다. 트랜잭션은 Transport Unit 하나로 짧게 유지합니다([Run the Client Adapter Daemon and the Main Server in one Bun process](../../adr/2026-10-29-run-daemon-and-main-server-in-one-bun-process.md) 참고).

| 설정 | 값 | 이유 |
|---|---|---|
| `journal_mode` | `WAL` | Transport Unit을 쓰는 동안에도 Visualization의 질의가 읽을 수 있게 합니다. |
| `synchronous` | `FULL` | `accepted`를 보낸 Transport Unit이 전원이 꺼져도 남게 합니다. |
| `foreign_keys` | `ON` | |
| `busy_timeout` | 설정 값 | 쓰기 잠금을 기다리는 최대 시간입니다. 넘으면 Transport Unit을 `unavailable`로 거절합니다. |
| `mmap_size` | `0` | 메모리 매핑한 파일 페이지가 프로세스의 RSS를 늘리므로 켜지 않습니다. |

### 설정

설정 파일([Client Adapter Daemon 구현](007.CLIENT_ADAPTER_DAEMON.md#설정))의 `[main_server]` 표에 둡니다.

| 항목 | 키 | 기본값 | 설명 |
|---|---|---|---|
| 데이터 파일 | `data_file` | `$XDG_DATA_HOME/agentoscope/agentoscope.db` | SQLite 데이터베이스 파일의 경로입니다. 상대 경로는 설정 파일이 있는 디렉터리를 기준으로 합니다. 디렉터리가 없으면 프롬프트 원문을 다른 계정이 읽지 못하도록 권한 `0700`으로 만듭니다. |
| 쓰기 잠금 대기 시간 | `busy_timeout_ms` | `5000` | `busy_timeout`(밀리초)입니다. Daemon의 Ack 타임아웃보다 짧아야 합니다. |

`XDG_DATA_HOME`이 없거나 절대 경로가 아니면 `~/.local/share`를 씁니다.

## 스키마

테이블, 열, 제약 조건, 인덱스와 DDL은 [Table Definition](009.TABLE_DEFINITION.md)에서 정의합니다. [Data Architecture의 Entity](../001.model/008.DATA_ARCHITECTURE.md#entity-목록)마다 테이블을 하나 두고, 파생 데이터를 만든 구성 규칙의 버전을 담는 `derivation` 테이블을 더합니다.

## 쓰기

Transport Unit 하나를 트랜잭션 하나로 처리합니다. [Data Architecture의 쓰기](../001.model/008.DATA_ARCHITECTURE.md#쓰기) 3번이 이 트랜잭션입니다.

1. `BEGIN IMMEDIATE`로 쓰기 잠금을 잡습니다. 쓰기 잠금 대기 시간 안에 잡지 못하면 `unavailable`로 거절합니다.
2. `session`, `agent`를 찾거나 추가하고, `ingest`를 추가합니다. `session`과 `agent`의 비어 있는 열은 `NULL`일 때만 채웁니다(예: `UPDATE session SET cwd = ? WHERE pk = ? AND cwd IS NULL`).
3. `event`를 추가합니다. `turn_id`는 Transport Unit의 `turn.id`, `position`은 `turn.position`에 `events` 안 순서를 더한 값입니다. 중복은 `INSERT ... ON CONFLICT (session_pk, event_id) DO NOTHING`으로 건너뜁니다.
4. Transport Unit의 `turn.id`에 해당하는 `turn`, `llm_call`, `tool_call`, `compaction`의 행을 지우고, `event`에서 그 Turn의 행을 `position` 순으로 읽어 다시 만듭니다. 3번에서 새로 추가한 `event` 행이 있으면, 같은 `agent_pk`에서 `status`가 `in_progress`인 다른 `turn` 행의 `status`를 `errored`로 바꿉니다.
5. `ingest`의 `stored_count`를 채우고 `COMMIT`합니다.
6. `COMMIT`이 끝난 뒤에 `accepted`를 돌려줍니다.

어느 단계에서든 오류가 나면 `ROLLBACK`하고 `unavailable`로 거절합니다.

4번에서 Turn의 행을 다시 만드는 규칙은 다음과 같습니다. 받는 대로 저장할 때와 [파생 데이터를 모두 다시 만들 때](#스키마-버전) 같은 규칙을 씁니다.

- Turn 안 위치 `0`에 그 Turn을 시작한 `user_message`(`event_id`가 `turn_id`와 같은 행)가 없으면 `turn` 행을 만들지 않습니다. 그 Turn의 `event` 행은 원본 데이터로만 남습니다.
- `status`는 먼저 그 Turn의 `event` 행으로 정합니다. 그 결과가 `in_progress`이고, 같은 `agent_pk`에 그 Turn의 `event` 행 가운데 가장 먼저 받은 것(`ingest_id`가 가장 작은 것)보다 나중에 받은 다른 Turn의 `event` 행이 있으면 `errored`입니다. 그래서 4번에서 `errored`로 바꾼 결과와 파생 데이터를 모두 다시 만든 결과가 같고, `errored`가 된 Turn은 늦게 온 `event` 행 때문에 다시 `in_progress`가 되지 않습니다.
- Core가 모르는 `type`의 `event` 행은 `status`와 `ended_at_us`를 정할 때 쓰지 않습니다. 받은 순서를 비교할 때는 씁니다.

## 읽기

LLM Call의 input은 같은 `agent_pk`의 `event`를 범위로 읽습니다.

1. Core가 그 Agent의 `turn` 행(`turn_id`, `started_at_us`, `ingest_id`)을 [Agent 안 Turn의 순서](../001.model/003.domain_model/006.TURN.md#구성-규칙)로 정렬합니다. 이 순서는 Core에만 두며, 질의는 이 순서로 정렬하지 않습니다.
2. 범위의 시작은 대상 LLM Call보다 앞에 있는 가장 가까운 `compaction` 행입니다. Core가 그 Agent의 `compaction` 행(`turn_id`, `position`)에서 찾고, 없으면 그 Agent의 첫 Turn부터 읽습니다.
3. 시작 Turn부터 대상 Turn까지 Turn마다 `event_by_turn` 인덱스로 `position` 범위를 읽습니다. 인덱스 순서대로 읽으므로 정렬하려고 본문을 모으지 않습니다.

```sql
-- Turn 하나에서 읽는 범위입니다. :types는 Core가 아는 type의 JSON 배열입니다.
SELECT event_id, turn_id, position, type, timestamp_us, body
FROM event
WHERE agent_pk = :agent_pk AND turn_id = :turn_id
  AND position >= :from_position AND position < :to_position
  AND type IN (SELECT value FROM json_each(:types))
ORDER BY position, pk;
```

- Core가 모르는 `type`의 `event`와, `turn` 행이 없는 Turn의 `event`는 input에 넣지 않습니다.
- 이 질의는 읽기 전용 연결을 따로 열어 트랜잭션 하나(스냅숏 하나)로 실행하고, 다 읽거나 그만 읽으면 연결을 닫습니다. 같은 연결에서 읽기를 오래 열어 두면 그 연결의 다른 질의도 같은 스냅숏을 보게 되고, `bun:sqlite`가 캐시한 같은 질의를 함께 쓰면 서로의 진행을 되돌리기 때문입니다.

Session 목록의 시작 시각은 그 Session의 `agent`에 속한 `turn.started_at_us`의 최솟값입니다. Turn이 없는 Session은 처음 받은 시각(그 Session의 `ingest.received_at_us`의 최솟값)으로 정렬합니다.

`event.body`를 읽는 질의는 `.get()`이나 `.iterate()`로 한 행씩 처리합니다. `.all()`로 결과를 모으지 않습니다([Visualization](010.VISUALIZATION.md#큰-데이터-조회) 참고). 목록에 필요한 작은 값(프롬프트의 앞부분, LLM 호출 오류)은 SQLite의 JSON 함수(`->`, `->>`)로 꺼냅니다.

## 스키마 버전

- 스키마 버전은 `PRAGMA user_version`에 둡니다. Main Server는 시작할 때 버전을 확인하고, 낮으면 순서대로 마이그레이션한 뒤 Transport Unit을 받습니다.
- 원본 데이터의 테이블은 내용을 잃지 않게 마이그레이션합니다.
- 파생 데이터의 테이블은 마이그레이션하지 않고 지운 뒤 다시 만들어도 됩니다.
- 스키마 버전이 Main Server가 아는 것보다 높으면 데이터 파일을 열지 않습니다.
- `derivation.version`이 Main Server가 가진 구성 규칙의 버전과 다르면(행이 없을 때를 포함합니다), Main Server는 파생 데이터를 모두 지우고 `event`로 다시 만듭니다. 다시 만드는 동안 받은 Transport Unit은 `unavailable`로 거절합니다.
  - 파생 데이터와 `derivation` 행을 트랜잭션 하나로 지운 뒤, `event`의 Turn을 키 순서로 200개씩 트랜잭션 하나로 다시 만듭니다. 트랜잭션 사이에는 이벤트 루프를 놓아 주어 같은 프로세스의 다른 일이 멈추지 않게 합니다.
  - 모두 만든 뒤에 `derivation.version`을 씁니다. 도중에 종료되면 다음에 시작할 때 처음부터 다시 만듭니다.

## Session 삭제

Session 하나를 트랜잭션 하나로 지웁니다. 그 Session의 `tool_call`, `llm_call`, `compaction`, `turn`, `event`, `ingest`, `agent`, `session` 행을 이 순서로 지웁니다.

## 결정되지 않은 사항

- 큰 `event.body`를 압축하거나 따로 저장할지. 압축하면 `body`의 `json_valid` 제약을 바꿔야 하므로, 되풀이되는 input을 한 번만 저장하는 방법([Data Architecture](../001.model/008.DATA_ARCHITECTURE.md#결정되지-않은-사항) 참고)과 함께 정합니다.
- 백업 방법(예: `VACUUM INTO`)
