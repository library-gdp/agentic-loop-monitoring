# 009.VISUALIZATION.md

이 문서는 Visualization이 사용자에게 보여 주는 화면과, 그 화면에 필요한 데이터를 정합니다. 화면은 [Intent](../../intent/INTENT-1.0.md#proposed-outcome)의 기대 결과인 역추적, LLM Call 단위의 input과 output 확인, 잘못된 판단 지점 찾기, 토큰 사용 파악을 돕습니다. Visualization의 역할과 의존 관계는 [Application Architecture](007.APPLICATION_ARCHITECTURE.md#visualization)를, 화면이 읽는 데이터의 구조는 [Domain Model](003.domain_model/001.OVERVIEW.md)과 [Data Architecture](008.DATA_ARCHITECTURE.md)를 따르며, 이 문서는 그것을 바꾸지 않습니다. 화면에 필요하지만 지금의 모델에 없는 데이터는 [빠진 데이터](#빠진-데이터)에 모았습니다. 화면을 그리는 기술과 접속 방법은 다루지 않습니다. 용어는 [Glossary](002.GLOSSARY.md)를 따릅니다.

## 사용자 이야기

사용자는 에이전트의 결과를 검증하다가 실패라고 판단한 Session을 열어, 에이전트가 거친 과정을 거슬러 올라갑니다.

1. **Session 목록**에서 확인할 Session을 고릅니다. 목록은 마지막 활동 시각이 늦은 순서이며, Session마다 무엇을 하던 Session이고 그 안에서 무슨 일이 있었는지를 요약해 보여 줍니다.
2. Session을 열면 **Session Graph**가 보입니다. Session Graph는 Node와 Edge로 이루어진 DAG이며, git 히스토리처럼 위에서 아래로 시간이 흐릅니다.
3. Agent 하나의 Node는 **Lane** 하나에 세로로 놓입니다. LLM Call은 Lane 위에 차례로 놓이고, LLM Call이 요청한 Tool Call은 그 LLM Call 아래에 매달립니다.
4. Subagent를 띄우면 그 Tool Call에서 새 Lane이 갈라져 Subagent의 작업이 그려지고, Subagent의 결과를 받은 부모 Agent의 LLM Call에서 다시 합쳐집니다.
5. Node에 마우스를 올리거나 키보드로 고르면 **Tooltip**이 요약을 보여 줍니다. Node를 누르면 **Detail Panel**이 열려 그 Node의 전체 내용을 보여 줍니다. LLM Call이면 input과 output 전체입니다.

이 이야기는 처음 제안된 이야기를 [검토 결과](#검토-결과)에 따라 보완한 것입니다. 처음 이야기의 Line을 이 문서에서는 Lane이라고 부릅니다.

### Intent와의 대응

| Intent의 기대 결과 | 화면 |
|---|---|
| 1. 역추적 | Session Graph에서 Turn, Loop, LLM Call, Tool Call, Subagent를 순서대로 따라갑니다. |
| 2. LLM Call 단위로 input과 output 확인 | Detail Panel의 Input Delta, 전체 input, output |
| 3. 잘못된 판단 지점 찾기 | Input Delta, Signal 사이 이동, Node 링크 |
| 4. 토큰 사용 파악 | Session Graph의 Token 열과 Context 그래프, Turn, Lane, Session의 Token 합계, Session 목록의 Token 합계순 정렬 |

## 검토 결과

처음 제안된 이야기를 항목마다 검토한 결과입니다.

| 처음 이야기 | 판단 | 이유와 보완 |
|---|---|---|
| Session 목록에서 Session마다 요약을 보고 고른다 | 유지 | 요약은 기록된 사실로 만듭니다. 에이전트가 기록한 Session 제목, 첫 프롬프트와 마지막 프롬프트, 수와 합계, Signal입니다. LLM으로 요약문을 만들지 않습니다. 프롬프트와 Tool Call 결과의 원문을 다른 모델에 보내야 하고, 기록에 없는 내용이 섞일 수 있기 때문입니다. |
| 목록은 최신순이다 | 보완 | 시작 시각이 아니라 마지막 활동 시각을 기준으로 합니다. 며칠 전에 시작해 오늘 이어 간 Session도 사람이 방금 결과를 검증한 Session이기 때문입니다. 시작 시각순과 Token 합계순도 고를 수 있게 합니다. |
| Session을 DAG로 그린다 | 유지 | 모든 Edge는 앞 Node의 결과가 뒤 Node로 들어가는 방향이므로 순환이 생기지 않습니다. |
| LLM reasoning과 Tool Call이 각각 Node로 한 줄에 놓인다 | 보완 | LLM Call 하나가 Tool Call 여러 개를 한 번에 요청하고 에이전트가 이를 함께 실행할 수 있습니다. 이 Tool Call들을 한 줄에 차례로 놓으면 순서가 있는 것처럼 보입니다. LLM Call만 Lane 위에 차례로 놓고, Tool Call은 요청한 LLM Call 아래에 나란히 매답니다. 그러면 Loop 하나가 한 덩어리로 보입니다. reasoning은 Node를 따로 두지 않고 LLM Call Node의 output으로 보여 줍니다. reasoning, 텍스트, Tool Call 요청이 한 응답에서 나오기 때문입니다. |
| Agent 하나는 위에서 아래로 일직선이다 | 대체로 유지 | Turn이 여러 개여도 Lane 하나에 이어 그리고, 각 Turn은 Prompt Node에서 시작합니다. 다만 사용자가 대화를 앞 지점으로 되돌리고 다시 진행하면 Agent 하나 안에서도 대화가 갈라집니다. 지금의 모델은 이를 나타내지 못합니다([빠진 데이터](#빠진-데이터)의 D1). |
| Subagent가 생기면 새 Line이 생기고 그 Line에 Subagent의 작업이 보인다 | 유지 | 갈라지는 곳은 Subagent를 띄운 Tool Call이고, 합쳐지는 곳은 그 Tool Call의 결과를 input으로 받은 부모 Agent의 LLM Call입니다. 연결 정보가 없는 경우, 부모가 Subagent를 기다리지 않는 경우, 같은 Subagent를 여러 번 이어 가는 경우는 [Subagent의 Edge Case](#subagent)를 참고하세요. |
| Node에 마우스를 올리면 Tooltip에 Node의 정보가 나온다 | 보완 | Tooltip은 요약에만 씁니다. LLM Call의 input은 수백 KB에 이를 수 있어 Tooltip에 담을 수 없고, 마우스를 떼면 사라져 읽거나 복사할 수 없습니다. 그래서 Tooltip은 긴 원문을 앞 200자까지만 보이고, Node를 누르면 고정된 Detail Panel을 열어 전체 원문을 보입니다. 마우스가 없는 환경을 위해 키보드로도 Node를 고를 수 있어야 합니다. |

## 더 나은 방향

처음 이야기에 더해 다음을 제안합니다. 각 항목은 [화면 구성](#화면-구성)에 반영했습니다.

1. **LLM Call은 Lane 위에, Tool Call은 LLM Call 아래에 둡니다.** Agent의 판단(LLM Call)이 세로선 하나로 이어지고, 그 판단으로 취한 action(Tool Call)이 바로 아래에 붙습니다. 병렬로 요청한 Tool Call이 차례로 실행된 것처럼 보이지 않습니다.
2. **input은 Input Delta부터 보여 줍니다.** LLM Call의 input은 앞 LLM Call의 input에 몇 가지가 더해진 것입니다. 매번 전체 input을 보여 주면 같은 내용을 되풀이해 읽어야 합니다. 그 LLM Call에서 새로 들어온 것(앞 LLM Call의 output, Tool Call 결과, 새 프롬프트, Compaction 요약)을 먼저 보여 주면, 모델이 무엇을 새로 보고 그 판단을 했는지 바로 찾을 수 있습니다. 전체 input도 펼쳐 볼 수 있습니다.
3. **Token을 그래프 옆에 둡니다.** LLM Call 행마다 Token 막대를 같은 높이에 두고, 화면 머리에 LLM Call별 Context 크기 그래프를 둡니다. Context가 어디서 커지고 Compaction으로 얼마나 줄었는지, 어느 Tool Call 결과 뒤에 input이 크게 늘었는지 보입니다. Subagent의 Token은 Subagent를 띄운 Tool Call과 Lane의 머리에 하위 Subagent까지 더한 합계로 보여 줍니다.
4. **마지막 Turn에서 시작합니다.** 사람은 보통 마지막 결과를 보고 실패라고 판단합니다. Session Graph를 열 때 마지막 Turn을 펼치고 앞 Turn은 접어 두면, 실패를 본 지점에서 위로 거슬러 올라갈 수 있습니다.
5. **Signal 사이를 건너뜁니다.** LLM 호출 오류, Tool Call 실패, `max_tokens`나 `refusal`로 끝난 LLM Call, 중단된 Turn처럼 실패의 단서가 될 수 있는 기록된 사실을 Signal로 표시하고, 앞뒤 Signal로 건너뛸 수 있게 합니다. Signal은 실패를 판정하지 않습니다. 실패 판단은 사람이 합니다.
6. **세로 순서를 두 가지로 둡니다.** 기본인 Grouped 보기는 Subagent의 Node를 그 Subagent를 띄운 Loop 바로 아래에 모읍니다(git의 `--topo-order`와 비슷합니다). Chronological 보기는 모든 Agent의 Node를 시각순으로 섞어 Subagent들이 동시에 일한 모습을 보여 줍니다(git의 `--date-order`와 비슷합니다).
7. **접고 펼칩니다.** Turn, Subagent의 Lane, Loop의 Tool Call을 접을 수 있습니다. 접힌 것은 수와 Token 합계만 보여 줍니다. Session이 길어도 화면이 가볍습니다.
8. **Node마다 링크를 둡니다.** 찾아낸 판단 지점을 나중에 다시 열거나 다른 사람에게 보여 줄 수 있습니다.
9. **기록의 한계를 드러냅니다.** 추정한 시각, 기록으로 다시 구성한 input, 에이전트가 기록하지 않아 빠진 input, 유실된 기록을 표시합니다. 기록되지 않은 것을 일어나지 않은 것으로 오해하지 않게 합니다.
10. **사람의 판단을 남길 수 있게 합니다.** 다음 단계의 제안입니다. Session이나 Turn에 실패 표시를 하고, 잘못된 판단 지점이라고 본 Node에 메모를 남깁니다. 이 기록은 워크플로우와 하네스를 고치는 근거가 되고, Session 목록에서 실패한 Session만 거를 수 있게 합니다. 지금의 데이터에는 이를 둘 곳이 없습니다([빠진 데이터](#빠진-데이터)의 D8).

### 검토한 다른 방향

| 방향 | 판단 |
|---|---|
| Session, Agent, Turn, Loop로 차례로 들어가는 목록 화면 | 큰 Session에서도 가볍지만, Subagent와 부모 Agent가 시간상 어떻게 맞물렸는지와 판단의 흐름을 한 화면에서 보기 어렵습니다. Session Graph의 접기와 Detail Panel로 같은 탐색을 할 수 있으므로 기본 화면으로 두지 않습니다. 보조 화면으로는 둘 수 있습니다. |
| 가로축이 시간인 타임라인(Gantt) | 동시성과 시간이 어디에 쓰였는지는 잘 보이지만, 짧은 LLM Call과 Tool Call이 점처럼 작아져 판단의 순서와 내용을 읽기 어렵습니다. Chronological 보기와 Duration 표시로 일부를 대신합니다. |
| Node를 자유롭게 배치한 그래프 | Node가 많으면 읽기 어렵고 시간 순서가 위치로 드러나지 않습니다. |

## 화면 구성

Visualization은 Session 목록과 Session Graph 두 화면으로 이루어집니다. Session 목록에서 Session을 고르면 Session Graph가 열리고, Session Graph 안에서 Tooltip과 Detail Panel을 엽니다. 아래 그림의 내용은 예시입니다.

### Session 목록

```
+------------------------------------------------------------------------------------------+
| Sessions   Agent [all v]  cwd [all v]  Host [all v]  Period [7 days v]  [x] Signals only |
|            Sort (o) Last activity  ( ) Started  ( ) Tokens                               |
+------------------------------------------------------------------------------------------+
| Fix the flaky login test                                       opencode     ~/work/api   |
|   Last: It still fails on CI. Check the retry logic.                                     |
|   11-14 14:32 .. 15:04  active 18m   Turns 3 (1 interrupted)  Subagents 2                |
|   LLM Calls 41  Tool Calls 88 (3 failed)   Tokens in 120K  cache 1.0M  out 48K           |
|   Signals 5                                                                              |
+------------------------------------------------------------------------------------------+
| Add a dark mode toggle                                         claude-code  ~/work/web   |
|   11-14 11:05 .. 11:20  active 15m   Turns 1  Subagents 0                                |
|   LLM Calls 9  Tool Calls 17   Tokens in 30K  cache 180K  out 9K                         |
+------------------------------------------------------------------------------------------+
|                                   [ Load more ]                                          |
+------------------------------------------------------------------------------------------+
```

| 영역 | 내용 |
|---|---|
| 거르기 | 에이전트 id, 작업 디렉터리, 머신, 기간, Signal이 있는 Session만 보기 |
| 정렬 | 마지막 활동 시각순(기본), 시작 시각순, Token 합계순 |
| 제목 | 에이전트가 기록한 Session 제목. 없으면 Main Agent의 첫 프롬프트 앞부분 |
| 마지막 프롬프트 | Main Agent의 마지막 Turn의 프롬프트 앞부분. Turn이 하나면 보이지 않습니다. |
| 정보 | 에이전트 id, 작업 디렉터리, 시작 시각과 마지막 활동 시각, 활동 시간 |
| 수 | Turn 수와 `completed`가 아닌 Turn의 수, Subagent 수, LLM Call 수, Tool Call 수와 실패 수 |
| Token | Token 합계. Input Token, Cache Read Token과 Cache Write Token의 합, Output Token을 보이고, 나머지 항목은 Tooltip으로 보입니다. |
| Signal | Session 안의 Signal 수 |
| 이어 보기 | 끝까지 내리면 다음 Session을 더 불러옵니다. |
| 동작 | Session 열기, Session 삭제([Session 단위 삭제](008.DATA_ARCHITECTURE.md#삭제와-보관)) |

- 활동 시간은 Turn Duration의 합입니다. Session의 시작과 끝 사이에서 Turn이 없던 시간은 들어가지 않습니다.

그림에서 Turn 1과 Turn 2는 접혀 있고 마지막 Turn인 Turn 3은 펼쳐져 있습니다. LLM Call 7이 Tool Call 세 개를 함께 요청했고, 그 가운데 `task`가 Subagent `explore`를 띄웠습니다. Subagent의 Lane은 `task`에서 갈라져 그 결과를 받은 LLM Call 8에서 합쳐집니다. LLM Call 8 뒤에 Compaction이 있었고, LLM Call 9가 요청한 `bash`가 끝나기 전에 사용자가 Turn을 중단했습니다. 오른쪽 Detail Panel은 LLM Call 8의 Input Delta, 곧 LLM Call 7의 output과 세 Tool Call의 결과를 보여 줍니다.

| 영역 | 내용 |
|---|---|
| 머리 | Session 제목, 에이전트 id, 작업 디렉터리, 시각, Session의 수와 Token 합계, Context 그래프, 보기 설정(Grouped 보기와 Chronological 보기, Tool Call 접기), Signal 이동 |
| 그래프 | Lane과 Node. 한 행에 Node 하나를 놓습니다. |
| Token 열 | 그래프의 행과 같은 높이에 Token 막대와 합계를 놓습니다. |
| Detail Panel | 고른 Node의 전체 내용. 닫으면 그래프가 넓어집니다. |

#### Node

| Node | 만드는 것 | 놓이는 곳 | Tooltip |
|---|---|---|---|
| Prompt | Turn을 시작한 `user_message` | Turn의 첫 행. Turn의 머리를 겸해 Turn의 `status`, LLM Call 수, Token 합계를 보이고 Turn을 접습니다. Subagent에서는 Lane의 머리도 겸합니다. | 프롬프트 앞부분, 시각, 길이. Subagent이면 Agent의 이름이나 종류와 띄운 Tool Call |
| LLM Call | LLM Call | Lane 위 | 모델, Stop Reason이나 LLM 호출 오류, `attempt`, Duration, Token Usage, 요청한 Tool Call의 이름, output 텍스트 앞부분 |
| Tool Call | Tool Call | 요청한 LLM Call 아래에 요청 순서대로 | 도구 이름, 인자 앞부분, 실패 여부, Duration, 결과 크기, 띄운 Subagent와 그 Token 합계 |
| Compaction | Compaction | Lane을 가로지르는 경계선 | `trigger`, 직전 컨텍스트의 토큰 수, 요약에 쓴 Token Usage, 요약 앞부분 |
| Interrupt | `turn_interrupted` | 중단된 Turn의 마지막 행 | 중단된 시각 |
| Context | 위 어느 것도 아니지만 LLM Call의 input에 들어간 Session Log Event | Lane 위의 작은 Node | 종류, 내용 앞부분 |
| Gap | 기록이 빠진 것으로 보이는 자리 | 빠진 자리에 점선으로 | 빠진 것으로 보는 근거 |

- 오류로 끝난 LLM Call, 실패한 Tool Call, 결과가 기록되지 않은 Tool Call, `max_tokens`나 `refusal`로 끝난 LLM Call은 모양을 달리하고 Signal로 셉니다.
- Node의 종류와 상태는 색만으로 구분하지 않고 모양과 글자를 함께 씁니다.
- Duration을 추정한 시각으로 계산했으면 추정이라고 표시합니다.

#### Edge

| Edge | 잇는 것 | 뜻 |
|---|---|---|
| Sequence | 같은 Lane에서 이웃한 Prompt, LLM Call, Compaction, Context, Interrupt | 뒤 Node의 input에 앞 Node가 들어갑니다. Turn이 바뀌어도 이어지며, Compaction을 지나면 앞의 내용이 요약으로 바뀝니다. |
| Request | LLM Call → Tool Call | LLM Call이 Tool Call을 요청했습니다. Tool Call의 결과는 같은 Lane의 다음 LLM Call의 input에 들어갑니다. |
| Spawn | Tool Call → Subagent의 Prompt | Tool Call이 Subagent를 띄웠습니다. |
| Return | Subagent의 마지막 Node → 부모 Agent의 다음 LLM Call | Subagent의 결과가 Tool Call의 결과로 부모 Agent에 돌아갔습니다. 다음 LLM Call이 없으면 그리지 않습니다. |

- 기록으로 연결을 알 수 없어 시각으로 추정한 Spawn과 Return은 점선으로 그립니다.

#### Lane

- Agent마다 Lane이 하나 있습니다. Main Agent의 Lane이 가장 왼쪽입니다.
- Subagent의 Lane은 부모 Agent의 Lane 오른쪽에 놓입니다. Spawn에서 시작해 Return에서 끝나며, 끝난 Lane의 자리는 뒤에 띄운 Subagent가 다시 씁니다. 그래서 Lane의 수는 동시에 일한 Subagent의 수만큼만 늘어납니다.
- Lane의 색은 Agent마다 정해 둡니다. 같은 Subagent를 다시 이어 가면 자리는 달라도 색은 같습니다.
- Subagent Lane의 머리에는 Agent의 이름이나 종류, Turn의 `status`, 하위 Subagent까지 더한 Token 합계를 보입니다. Agent의 이름이나 종류가 기록되지 않았으면 띄운 Tool Call의 이름과 프롬프트 앞부분으로 대신합니다([빠진 데이터](#빠진-데이터)의 D4).
- 접은 Lane은 Node 하나로 보입니다.

#### 세로 순서

- 같은 Agent 안에서는 Turn의 순서를, Turn 안에서는 Turn 안 위치의 순서를 따릅니다.
- Loop의 Tool Call은 LLM Call 바로 아래에 요청 순서대로 놓습니다. 그 Loop가 띄운 Subagent의 Node는 Tool Call 아래, 다음 LLM Call 위에 놓입니다.
- **Grouped 보기(기본)**: Subagent 하나의 Node를 한데 모읍니다. 한 Loop가 Subagent를 여러 개 띄웠으면 Tool Call 순서대로 하나씩 놓습니다. 동시에 일한 Subagent도 위아래로 나뉘어 보이지만 Lane은 나란히 있습니다.
- **Chronological 보기**: 모든 Agent의 Node를 시작 시각순으로 섞습니다. Subagent의 Node는 Spawn보다 위에, Return보다 아래에 놓지 않습니다.
- 세로 위치는 순서만 나타내고 시간 간격은 나타내지 않습니다. 오래 걸린 Node는 Duration으로 알 수 있습니다. Turn 사이에 쉰 시간이 길면 Prompt Node에 표시합니다.

#### Token 열

- LLM Call 행: input 크기(Input Token, Cache Read Token, Cache Write Token을 쌓은 막대)와 Output Token, Reasoning Token. 막대의 길이는 Session 안에서 가장 큰 값을 기준으로 합니다.
- Compaction 행: 직전 컨텍스트의 토큰 수와 요약에 쓴 Token
- Prompt Node(Turn의 머리), Subagent Lane의 머리, Subagent를 띄운 Tool Call: 합계
- 머리의 Context 그래프: LLM Call마다 input 크기를 점으로 잇고 Compaction의 자리를 표시합니다. 점을 누르면 그 LLM Call로 갑니다. 처음에는 Main Agent를 보이며, Subagent의 Lane을 고르면 그 Agent로 바뀝니다.
- 에이전트가 기록하지 않은 항목은 0으로 그리지 않고 비워 둡니다. 합계에 Token을 기록하지 않은 LLM Call이 있으면 그 수를 함께 보입니다.

#### 처음 열 때와 이동

- Main Agent의 마지막 Turn을 펼치고 나머지 Turn은 접은 채로, 마지막 Turn의 마지막 Node가 보이게 엽니다. Node 링크로 열면 그 Node가 보이게 엽니다.
- 앞뒤 Signal, 앞뒤 Turn으로 건너뜁니다.
- 키보드로 같은 Lane의 앞뒤 Node로 움직이고, 갈라지는 곳에서 Lane 사이를 움직입니다.
- 도구 이름과 Signal 종류로 거를 수 있습니다. 거르기에 맞지 않는 Node는 흐리게 보입니다.

### Tooltip

- Node에 마우스를 올리거나 키보드로 고르면 열립니다. 내용은 [Node](#node) 표의 Tooltip 열과 같습니다.
- 원문(프롬프트, output 텍스트, 도구 인자, 요약, 내용)은 앞 200자까지만 보입니다. 원문이 200자보다 길면 잘린 자리에 말줄임표를 붙이고 원문 전체의 크기를 함께 보여, 잘렸다는 것과 얼마나 큰지 알 수 있게 합니다.
- 원문은 Tooltip을 열 때 앞 200자만 읽습니다. 원문이 수백 KB여도 Tooltip을 여는 데 원문 전체를 읽지 않습니다.
- 전체 원문은 Node를 눌러 연 [Detail Panel](#detail-panel)에서 봅니다.

### Detail Panel

Node를 누르면 열리고, 다른 Node를 누르거나 닫을 때까지 그대로 있습니다.

| Node | 내용 |
|---|---|
| LLM Call | 모델, Stop Reason, LLM 호출 오류, `attempt`, 시작 시각과 끝난 시각, Duration, Token Usage, Context 크기. output의 reasoning, 텍스트, Tool Call 요청(각 Tool Call Node로 가는 링크). input의 Input Delta(기본)와 전체 input. 같은 Agent의 앞뒤 LLM Call로 가는 링크 |
| Tool Call | 도구 이름, 인자 전체, 결과 전체, 실패 여부, 요청한 시각과 끝난 시각, Duration. 띄운 Subagent로 가는 링크와 그 Token 합계 |
| Prompt | 프롬프트 전체. Subagent이면 띄운 Tool Call로 가는 링크 |
| Compaction | `trigger`, 직전 컨텍스트의 토큰 수, 요약 전체, 요약을 만든 모델과 Token Usage. 요약으로 바뀐 범위(앞 Compaction이나 Agent의 처음부터 이 Compaction까지) |
| Context | 내용 전체 |
| Gap | 빠진 것으로 보는 근거(건너뛴 Turn 안 위치, 버려진 Session Log Event의 수 등) |

LLM Call의 input은 다음과 같이 보여 줍니다.

- input의 항목마다 Session Log Event의 종류, 시각, 크기를 먼저 보이고, 내용은 펼칠 때 읽습니다. 큰 내용은 나누어 불러옵니다. 텍스트가 아닌 내용(예: 이미지)은 종류와 크기만 보입니다.
- Input Delta를 보일 때 앞 LLM Call 뒤에 Compaction이 있었으면, 요약으로 바뀌어 input에서 빠진 범위도 함께 표시합니다.
- input은 기록으로 다시 구성한 것이며 모델이 받은 요청과 다를 수 있다고 표시합니다. 에이전트가 기록하지 않은 input(예: 시스템 프롬프트, 지침 파일, 도구 정의)은 없고, 에이전트가 요청을 보내기 전에 고친 내용(예: 오래된 도구 결과를 지운 것)은 반영되지 않습니다.
- 그 에이전트가 기록하지 않는 input의 종류를 input 위에 안내합니다([빠진 데이터](#빠진-데이터)의 D7).

## Edge Case

처음 이야기에서 다루지 않은 경우와 화면에서의 처리입니다. 지금의 모델로 처리할 수 없는 경우는 [빠진 데이터](#빠진-데이터)의 번호를 적었습니다.

### Session을 고를 때

| 경우 | 처리 |
|---|---|
| Main Agent의 기록이 아직 오지 않았습니다. | 제목 자리에 Main Agent의 기록이 없다고 표시하고 Subagent의 첫 프롬프트를 보입니다. |
| Turn이 하나도 없습니다(Turn을 시작한 `user_message`가 유실됨 등). | 기록된 시각이 없으므로 처음 받은 시각(수신 기록의 `received_at`)으로 정렬하고 그 사실을 표시합니다. |
| 진행 중인 Turn이 있습니다. | 진행 중이라고 표시합니다. 실시간으로 갱신하지 않으며, 다시 불러오면 그사이 받은 기록이 보입니다. |
| 며칠 뒤에 이어 갔습니다. | 마지막 활동 시각순이므로 다시 위로 옵니다. 활동 시간에는 쉰 시간이 들어가지 않습니다. |
| 앞 Session을 이어 가거나 갈라내어 만든 Session입니다. | 두 Session을 잇지 못합니다. 앞 Session의 내용이 새 Session에 다시 기록되었을 수 있습니다(D11). |
| Session이 매우 많습니다. | 이어 보기로 나누어 불러옵니다. |

### Agent 안의 흐름

| 경우 | 처리 |
|---|---|
| LLM Call 하나가 Tool Call 여러 개를 요청했습니다. | LLM Call 아래에 나란히 매답니다. 실제로 실행된 순서와 시작 시각은 기록되지 않을 수 있습니다(D6). |
| Agent에 Turn이 여러 개입니다. | Lane 하나에 이어 그리고, Turn마다 Prompt Node에서 시작합니다. |
| 사용자가 대화를 앞 지점으로 되돌린 뒤 다시 진행했습니다. | 지금은 알아볼 수 없어 되돌린 Node와 다시 진행한 Node가 한 줄에 이어져 보이고, 뒤 LLM Call의 input에 되돌린 내용이 들어갑니다. 갈라진 지점에서 같은 Lane 안에 가지를 그려야 합니다(D1). 사람이 대화를 되돌린 지점은 잘못된 판단을 알아챈 지점일 때가 많습니다. |
| Compaction이 있습니다. | Lane을 가로지르는 경계선으로 그립니다. 경계선 위의 Node는 뒤 LLM Call의 input에서 요약으로 바뀌었습니다. 사용자가 Compaction만 요청한 Turn에는 Prompt와 Compaction만 있습니다. |
| LLM 호출 오류 뒤에 다시 시도했습니다. | 실패한 LLM Call과 다시 보낸 LLM Call이 차례로 보이고 `attempt`를 표시합니다. 실패한 시도를 기록하지 않는 에이전트에서는 실패한 시도가 보이지 않습니다. |
| LLM Call이 `max_tokens`나 `refusal`로 끝났습니다. | Signal로 표시합니다. output이 잘린 것은 실패의 원인이 되기 쉽습니다. |
| LLM Call의 output이 비어 있습니다. | 빈 응답이라고 표시합니다. |
| reasoning의 원문이 기록되지 않았습니다. | reasoning이 기록되지 않았다고 표시하고, Reasoning Token이 기록되었으면 그 수를 보입니다. |
| Tool Call의 결과가 기록되지 않았습니다. | 결과가 없다고 표시합니다. Turn이 중단되었거나, 에이전트가 종료되었거나, 아직 실행 중일 수 있습니다. |
| 모델이 응답하기 전에 Turn이 끝났습니다. | Prompt Node 하나와 Turn의 `status`만 보입니다. |
| Turn의 `status`가 `interrupted`, `errored`, `in_progress`입니다. | Prompt Node에 `status`를 보이고 Signal로 셉니다. `interrupted`인 Turn은 Interrupt Node로 끝납니다. |
| 에이전트가 넣은 지시문이나 사용자가 직접 실행한 명령처럼, LLM Call도 Tool Call도 아닌 기록이 input에 들어갔습니다. | Context Node로 그립니다. 지금 정의된 Session Log Event 종류로 나타낼 수 없으면 보이지 않습니다(D3). |
| 기록 일부가 유실되었습니다. | Turn 안 위치가 건너뛴 자리에 Gap Node를 그립니다. 자리를 알 수 없는 유실(Turn 없이 저장된 Session Log Event, 수신 기록의 버려진 Session Log Event)은 Lane의 머리에 표시합니다. |
| Agent가 쓰는 모델이 도중에 바뀌었습니다. | LLM Call마다 모델을 보입니다. |

### Subagent

| 경우 | 처리 |
|---|---|
| Subagent를 띄운 Tool Call을 알 수 없습니다(`subagent_id`가 없음). | 부모 Agent는 Agent의 `parent_id`로 압니다. Subagent의 첫 Turn이 시작된 시각에 실행 중이던 부모 Agent의 Tool Call에서 점선으로 갈라지게 합니다. 그런 Tool Call이 여럿이거나 없으면 가장 가까운 앞 LLM Call에서 갈라지게 합니다. |
| 부모 Agent의 기록이 없습니다. | Subagent의 Lane을 따로 그리고 부모 Agent의 기록이 없다고 표시합니다. |
| `subagent_id`가 가리키는 Agent의 기록이 없습니다. | Tool Call에 Subagent의 기록이 없다고 표시하고 Lane을 그리지 않습니다. |
| 한 Loop가 Subagent를 여러 개 띄웠습니다. | Lane이 그 수만큼 나란히 갈라지고 다음 LLM Call에서 함께 합쳐집니다. Lane이 많으면 접어서 묶습니다. |
| Subagent가 다시 Subagent를 띄웠습니다. | Subagent의 Lane에서 다시 갈라집니다. 깊어지면 접어서 보입니다. |
| 부모 Agent가 Subagent를 기다리지 않고 진행했습니다(백그라운드 실행). | Tool Call의 결과는 Subagent의 결과가 아니며, Subagent의 결과는 나중에 다른 input으로 들어옵니다. Lane은 Subagent의 마지막 Node까지 이어지고, 결과가 들어온 곳을 알 수 없으면 Return을 그리지 않습니다(D10). Chronological 보기에서 부모 Agent와 Subagent가 동시에 일한 것이 보입니다. |
| 끝난 Subagent에 다시 프롬프트를 보내 이어 갔습니다. | Subagent에 Turn이 여러 개 생깁니다. Turn마다 그 Turn을 시작한 Tool Call에서 같은 Agent의 Lane이 다시 갈라집니다. 어느 Tool Call이 어느 Turn을 시작했는지는 시각으로 추정합니다(D9). |
| Tool Call 없이 에이전트 내부 기능으로 Subagent가 생겼습니다. | 띄운 Tool Call이 없으므로 시각으로 추정한 점선으로 갈라집니다. |
| 부모와 자식이 아닌 Agent끼리 메시지를 주고받았습니다. | 지금의 모델은 부모와 자식 관계만 나타내므로, 그 메시지는 각 Agent의 input으로만 보입니다(D14). |
| Subagent의 기록이 부모 Agent의 Tool Call보다 먼저 왔습니다. | 모두 받은 뒤에는 문제가 없습니다. 진행 중인 Session에서는 부모의 Tool Call이 올 때까지 Spawn을 추정해 그립니다. |

### 크기와 시간

| 경우 | 처리 |
|---|---|
| Node가 수천 개입니다. | Node의 메타데이터만으로 그래프를 그리고 보이는 행만 그립니다. 접힌 Turn은 합계만 불러옵니다. |
| 원문이 매우 큽니다. | Tooltip은 앞 200자만 보이고, Detail Panel은 전체를 나누어 불러옵니다. |
| LLM Call의 시작 시각을 추정했습니다. | Duration에 추정이라고 표시합니다. |
| Tool Call의 실행 시작 시각이 기록되지 않았습니다. | Tool Call의 Duration을 요청한 시각부터 잽니다. 병렬로 요청한 Tool Call의 Duration은 실제보다 길게 보일 수 있습니다(D6). |
| 시각이 거꾸로 기록되었습니다. | Node의 순서는 Turn 안 위치를 따르고, Session 목록은 기록된 시각대로 정렬합니다. 끝이 시작보다 앞인 Duration은 음수로 보이지 않고 시각이 거꾸로라고 표시합니다. |

| 일부 | 필드는 있지만 에이전트가 기록할 때만 값이 있습니다. |

| 없음 | 지금의 모델에 없습니다. [빠진 데이터](#빠진-데이터)의 번호를 적었습니다. |
| 얻을 수 없음 | 에이전트가 기록하지 않아 얻을 수 없습니다. |

## 빠진 데이터

화면에 필요하지만 지금의 모델에 없는 데이터입니다. 에이전트가 기록하지 않는 정보는 만들어 내지 않으므로([Intent](../../intent/INTENT-1.0.md#constraints)), Plugin이 아는 D7과 사용자가 만드는 D8을 빼면 에이전트가 기록하는 경우에만 더할 수 있습니다. 더할 곳은 후보이며, 모델을 바꿀 때 정합니다.

| 우선순위 | 뜻 |
|---|---|
| 높음 | 없으면 화면이 기록과 다르게 보입니다. |
| 중간 | 없어도 화면을 만들 수 있지만, 대신하는 값이 부정확하거나 원하는 것을 찾기 어렵습니다. |
| 낮음 | 있으면 분석에 도움이 됩니다. |

| # | 데이터 | 쓰는 곳 | 에이전트의 기록 | 더할 곳(후보) | 우선순위 |

### 정해야 하는 규칙

화면이 기대는 규칙 가운데 아직 정하지 않은 것입니다.

| 규칙 | 문서 | 화면에 미치는 영향 |
|---|---|---|
| Agent 안 Turn의 순서 | [Turn](003.domain_model/006.TURN.md) | Lane의 세로 순서, LLM Call의 input |
| 일부 LLM Call만 기록한 Token 항목의 합계 | [Token Usage](003.domain_model/003.TOKEN_USAGE.md#결정되지-않은-사항) | 합계를 보이는 방법. 이 문서는 기록된 값의 합과 기록하지 않은 LLM Call의 수를 함께 보이자고 제안합니다. |
| 오류로 끝난 LLM Call을 뒤 LLM Call의 input에 넣을지 | [LLM Call](003.domain_model/008.LLM_CALL.md#결정되지-않은-사항) | Input Delta에 실패한 시도가 들어가는지 |
| 사용자가 중단한 Turn을 남길지 | [Intent](../../intent/INTENT-1.0.md#constraints), [Turn](003.domain_model/006.TURN.md) | Intent는 사용자가 중간에 멈춘 Turn을 버린다고 하지만, Domain Model은 그 Turn을 `interrupted`로 남깁니다. 이 문서는 남긴 Turn을 보여 주자고 제안합니다. 사람이 Turn을 멈춘 지점은 잘못된 판단을 알아챈 지점일 때가 많기 때문입니다. |

### 더해야 하는 질의

[Data Architecture의 읽기](008.DATA_ARCHITECTURE.md#읽기) 질의에 다음을 더해야 합니다. 모두 지금 저장하는 데이터로 계산할 수 있습니다.

| 질의 | 읽는 데이터 |
|---|---|
| Session 목록. 마지막 활동 시각순, 시작 시각순, Token 합계순으로 나누어 불러오며, Session마다 [Session 목록](#session-목록)의 수, 합계, 프롬프트 앞부분을 담습니다. | 원본 데이터의 Session, Agent, 수신 기록, 파생 데이터의 Turn, LLM Call, Tool Call, Compaction. 프롬프트는 원문 |
| Session Graph. Session의 모든 Agent의 Node 메타데이터이며 원문을 담지 않습니다. Turn 단위로 나누어 불러올 수 있어야 합니다. | 파생 데이터, 원본 데이터의 Agent, Session Log Event의 `type`, `position`, `timestamp` |
| Node 미리보기. 원문의 앞 200자와 원문 전체의 크기 | 원본 데이터의 Session Log Event |
| LLM Call의 Input Delta | 원본 데이터의 Session Log Event |
| Subagent까지 더한 Token 합계. Tool Call, Turn, Agent의 하위 트리 단위 | 원본 데이터의 Agent, 파생 데이터의 Tool Call, LLM Call, Compaction |
| Session의 Signal 목록 | 파생 데이터의 Turn, LLM Call, Tool Call, 원본 데이터의 Session Log Event의 `position`과 수신 기록 |

Session 목록과 Session Graph의 행마다 원문을 읽으면 질의가 느려집니다. 프롬프트와 도구 인자의 앞부분을 파생 데이터에 둘지, 질의할 때 원문에서 읽을지는 정하지 않았습니다.

## 결정되지 않은 사항

- 토큰 낭비의 기준([Intent](../../intent/INTENT-1.0.md#open-questions)의 6번). 기준이 정해지면 Signal에 더합니다. 후보는 같은 인자로 되풀이한 Tool Call, 큰 Tool Call 결과 뒤의 input 증가, 낮은 cache 적중, 오류로 버려진 LLM Call의 Token, Compaction에 쓴 Token입니다.
- [빠진 데이터](#빠진-데이터)를 모델에 더할지와 그 형식
- 사람의 판단(D8)을 저장한다면 그 데이터의 소유자와 수명. 지금 Main Server의 데이터는 Transport Unit으로 받은 것과 그것으로 계산한 것뿐입니다.
- 프롬프트와 도구 인자의 앞부분을 파생 데이터에 둘지
- 프롬프트와 Tool Call 인자를 검색할지
- 텍스트가 아닌 내용(예: 이미지)을 보여 줄지
