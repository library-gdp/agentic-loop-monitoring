# 003.OPENCODE_SESSION_LOG.md

이 문서는 OpenCode v1(1.19.x)의 Session Log가 어떤 개념(session, message, part, step, 이벤트)으로 이루어지는지, 그 개념이 DB의 어느 테이블과 이벤트에 어떤 순서로 기록되는지 실제 기록과 함께 설명합니다. 테이블과 열의 전체 목록은 [OpenCode v1 데이터 아키텍처](002.OPENCODE_DATA_ARCHITECTURE.md)를, DB 옆의 `-wal`, `-shm` 파일은 [OpenCode v1 WAL과 SHM](001.OPENCODE_WAL_AND_SHM.md)을 참고하세요.

## 개념

### 구성

```
session (ses_…)        대화 하나. Subagent는 자신의 child session을 가집니다.
└─ message (msg_…)     한 번의 발화. user 또는 assistant입니다.
   └─ part (prt_…)     message를 이루는 내용 조각. 글, 추론, tool 호출 등입니다.

event (evt_…)          session, message, part를 바꿀 때마다 덧붙는 기록입니다.
```

session, message, part는 지금의 상태이고, 이벤트는 그 상태에 이르기까지 바뀐 내역입니다. OpenCode는 바꿀 내용을 이벤트로 기록하면서 그 내용을 `session`, `message`, `part` 테이블에 반영(투영)합니다.

사용자 입력 하나를 처리하는 동안 OpenCode는 LLM을 여러 번 부를 수 있습니다. 부를 때마다 assistant message가 하나씩 생기며, 모두 같은 user message를 `parentID`로 가리킵니다.

```
user message                        사용자 입력
assistant message (parentID: user)  LLM 호출 1. tool을 호출하고 끝남(finish: tool-calls)
assistant message (parentID: user)  LLM 호출 2. tool 결과를 받고 다시 tool을 호출함(finish: tool-calls)
assistant message (parentID: user)  LLM 호출 3. 답을 마침(finish: stop)
```

### Session

session은 대화 하나입니다. `session` 테이블의 행 하나이며 id는 `ses_`로 시작합니다. 작업 디렉터리, 제목, 사용 중인 agent와 model, session을 만든 OpenCode 버전, 누적 비용과 토큰, 변경 요약(추가, 삭제한 줄 수와 파일 수)을 담습니다.

Subagent는 자신을 띄운 session과 별개인 child session에서 실행됩니다. child session은 자신을 띄운 session의 id를 `parentID`로 가집니다. 기록 순서는 [Subagent](#subagent)를 참고하세요.

### Message

message는 한 번의 발화입니다. `message` 테이블의 행 하나이며 id는 `msg_`로 시작합니다. message에는 본문이 없고, 본문은 그 message의 part에 있습니다. `role`에 따라 두 종류가 있습니다.

| `role` | 뜻 | 주요 필드 |
|---|---|---|
| `user` | 사용자 입력 하나 | `agent`, `model`(`providerID`, `modelID`, `variant`), `time.created`, `summary.diffs`(이 입력을 처리하는 동안 바뀐 파일) |
| `assistant` | LLM 호출 한 번의 응답 | `parentID`(답하는 user message), `agent`, `mode`, `providerID`, `modelID`, `variant`, `path`(`cwd`, `root`), `tokens`, `cost`, `finish`, `error`, `time.created`, `time.completed`, `summary`(compaction 요약이면 `true`) |

- assistant message의 `tokens`와 `cost`는 그 LLM 호출 하나의 값입니다. 누적 값은 session에 있습니다.
- `finish`는 LLM 응답의 종료 이유입니다. `tool-calls`는 tool을 호출하고 끝났다는 뜻이고, `stop`은 답을 마쳤다는 뜻입니다. 확인한 DB에는 이 두 값만 있습니다.
- `error`는 응답이 오류로 끝났을 때 채워집니다. 사용자가 중단하면 `name`이 `MessageAbortedError`입니다.

사용자가 입력하지 않은 user message와 LLM을 부르지 않은 assistant message도 있습니다. LLM을 부르지 않은 assistant message에는 `step-start`, `step-finish` part가 없습니다.

| 경우 | 기록 |
|---|---|
| compaction | compaction을 요청하는 user message(`compaction` part), 자동 compaction 뒤 작업을 이어 가라는 user message(synthetic `text` part) |
| 사용자의 shell 명령 | user message(synthetic `text` part `The following tool was executed by the user`), `bash` tool part 하나를 가진 assistant message |
| subtask로 실행하는 command | user message(`subtask` part), OpenCode가 `task` tool을 직접 실행한 assistant message(`task` tool part 하나) |

### Part

part는 message를 이루는 내용 조각입니다. `part` 테이블의 행 하나이며 id는 `prt_`로 시작합니다. 한 message 안에서는 id 순서가 part를 만든 순서입니다.

| `type` | 붙는 message | 내용 |
|---|---|---|
| `text` | user, assistant | 글입니다. `synthetic`이 `true`이면 사용자나 모델이 아니라 OpenCode가 넣은 글(첨부 파일을 읽은 결과, 안내 문구 등)입니다. |
| `file` | user | 첨부 파일입니다(`mime`, `filename`, `url`, `source`). |
| `agent` | user | 사용자가 `@이름`으로 부른 agent입니다. |
| `subtask` | user | Subagent에게 맡길 작업(`prompt`, `description`, `agent`, `model`, `command`)입니다. |
| `compaction` | user | compaction 요청입니다(`auto`, `overflow`, `tail_start_id`). |
| `step-start` | assistant | LLM 호출(step)의 시작입니다. `snapshot`은 그때 작업 디렉터리의 snapshot hash입니다. |
| `reasoning` | assistant | 모델의 추론입니다. 공급자가 추론을 암호화해 넘기면 `text`는 비어 있고 암호문이 `metadata`에 있습니다. |
| `tool` | assistant | tool 호출 하나입니다. 호출(`callID`, `tool`, `state.input`)과 결과(`state.output` 또는 `state.error`)를 함께 담습니다. |
| `step-finish` | assistant | step의 끝입니다(`reason`, `tokens`, `cost`, `snapshot`). `reason`과 같은 값을 assistant message의 `finish`에 채웁니다. |
| `patch` | assistant | step 동안 바뀐 파일(`files`)과 snapshot hash입니다. 바뀐 파일이 있을 때만 생깁니다. |

스키마에는 `snapshot`, `retry` part도 정의되어 있지만, 1.19.5 소스에서 이 두 part를 기록하는 곳은 찾지 못했습니다.

#### tool part의 상태

`tool` part는 `state.status`에 따라 필드가 다릅니다. `?`는 없을 수 있는 필드입니다.

| `state.status` | 기록하는 때 | 필드 |
|---|---|---|
| `pending` | 모델이 tool 호출을 출력하기 시작할 때 | `input`(빈 객체), `raw`(빈 문자열) |
| `running` | 호출 인자를 다 받았을 때. 실행 중에 tool이 진행 정보를 넘길 때마다 다시 기록합니다. | `input`, `time.start`, `title`?, `metadata`? |
| `completed` | 실행이 끝났을 때 | `input`, `output`, `title`, `metadata`, `time.start`, `time.end`, `time.compacted`?, `attachments`? |
| `error` | 실행이 실패했거나 거부, 중단되었을 때 | `input`, `error`, `metadata`?, `time.start`, `time.end` |

#### 토큰

`step-finish` part와 assistant message의 `tokens`는 공급자가 넘긴 사용량을 다음처럼 나눈 값입니다.

| 필드 | 값 |
|---|---|
| `input` | 입력 토큰에서 `cache.read`와 `cache.write`를 뺀 값 |
| `cache.read` | cache에서 읽은 입력 토큰 |
| `cache.write` | cache에 쓴 입력 토큰 |
| `output` | 출력 토큰에서 `reasoning`을 뺀 값 |
| `reasoning` | 추론 토큰 |
| `total` | 공급자가 넘긴 전체 토큰 |

그래서 LLM 호출 한 번의 입력 크기는 `input + cache.read + cache.write`입니다. session의 누적 토큰은 `step-finish` part의 값을 더한 것입니다.

### Step

step은 LLM 호출 한 번입니다. 테이블은 따로 없고, assistant message 안의 `step-start` part부터 `step-finish` part까지가 step 하나입니다. OpenCode는 LLM을 부를 때마다 assistant message를 새로 만들므로 assistant message 하나에는 보통 step이 하나 있습니다. 확인한 DB의 assistant message 15개도 모두 `step-start`와 `step-finish`가 하나씩이었습니다.

응답을 받는 도중 오류가 나 OpenCode가 다시 시도하면 같은 assistant message에서 응답을 다시 받습니다. 이때 앞선 시도에서 기록한 part는 지우지 않습니다.

### 이벤트

이벤트는 session, message, part를 바꾼 기록입니다. `event` 테이블의 행 하나이며 id는 `evt_`로 시작합니다.

| 열 | 내용 |
|---|---|
| `aggregate_id` | 이벤트가 속한 session의 id입니다. message와 part의 이벤트도 그것이 속한 session의 id로 기록됩니다. |
| `seq` | aggregate 안의 순번입니다. 0부터 1씩 늘며, aggregate마다 마지막 값을 `event_sequence`에 둡니다. |
| `type` | 이벤트 이름 뒤에 형식 버전을 붙인 것입니다(예: `message.part.updated.1`). |
| `data` | 이벤트 내용입니다. `session.created`와 `*.updated`는 바뀐 필드만이 아니라 바뀐 뒤의 대상 전체를 담습니다. |

v1 Session Log의 이벤트 중 DB에 기록하는 것은 다음 일곱 가지입니다. 소스에는 v2 session 이벤트(`session.next.*`)도 정의되어 있지만 확인한 DB에는 없습니다. 확인한 DB에 있는 이벤트는 `session.created.1`, `session.updated.1`, `message.updated.1`, `message.part.updated.1`뿐입니다.

| `type` | `data` | 기록하는 때 |
|---|---|---|
| `session.created.1` | `sessionID`, `info`(session) | session을 만들 때 |
| `session.updated.1` | `sessionID`, `info`(session) | 제목, agent와 model, 변경 요약, 되돌리기 상태 등 session 정보를 바꿀 때 |
| `session.deleted.1` | `sessionID`, `info`(session) | session을 지울 때 |
| `message.updated.1` | `sessionID`, `info`(message) | message를 만들거나 바꿀 때 |
| `message.removed.1` | `sessionID`, `messageID` | 되돌리기나 API 요청으로 message를 지울 때 |
| `message.part.updated.1` | `sessionID`, `part`(part), `time`(기록한 시각) | part를 만들거나 바꿀 때 |
| `message.part.removed.1` | `sessionID`, `messageID`, `partID` | 되돌리기나 API 요청으로 part를 지울 때 |

`message.part.delta`(스트리밍 중에 늘어난 글), `session.status`, `session.error`, `session.diff` 같은 이벤트는 실행 중인 클라이언트에 알리기만 하고 DB에는 기록하지 않습니다.

## 데이터 아키텍처와의 연결

### 개념과 테이블

| 개념 | 테이블 | 이벤트 |
|---|---|---|
| session | `session` 행 하나입니다. session 정보를 열로 펼쳐 저장합니다(`parent_id`, `title`, `tokens_input` 등). | `session.created.1`, `session.updated.1`, `session.deleted.1` |
| message | `message` 행 하나입니다. `data`는 message에서 `id`, `sessionID`를 뺀 JSON입니다. | `message.updated.1`, `message.removed.1` |
| part | `part` 행 하나입니다. `data`는 part에서 `id`, `sessionID`, `messageID`를 뺀 JSON입니다. | `message.part.updated.1`, `message.part.removed.1` |
| step | 테이블이 없습니다. assistant message의 `step-start` part부터 `step-finish` part까지입니다. | `message.part.updated.1` |
| 이벤트 | `event` 행 하나입니다. aggregate별 마지막 `seq`는 `event_sequence`에 있습니다. | |

### 이벤트를 테이블에 반영하는 방식

| 이벤트 | 테이블에 하는 일 |
|---|---|
| `session.created.1` | `info`로 `session` 행을 추가합니다. |
| `session.updated.1` | `info` 전체로 `session` 행을 덮어씁니다. |
| `session.deleted.1` | `session` 행을 지웁니다. 외래 키로 이어진 `message`, `part` 등의 행도 함께 지워집니다. |
| `message.updated.1` | `message` 행을 추가합니다. 이미 있으면 `data`를 바꿉니다. |
| `message.removed.1` | `message` 행과 그 part를 지웁니다. 지운 `step-finish`의 토큰과 비용은 session 누적 값에서 뺍니다. |
| `message.part.updated.1` | `part` 행을 추가합니다. 이미 있으면 `data`를 바꿉니다. `step-finish`이면 토큰과 비용을 session 누적 값에 더합니다. |
| `message.part.removed.1` | `part` 행을 지웁니다. `step-finish`이면 토큰과 비용을 session 누적 값에서 뺍니다. |

- 행을 처음 추가할 때 `message.time_created`는 message의 `time.created`이고, `part.time_created`는 그 이벤트의 `time`입니다. 행을 바꾸면 `time_updated`가 그때의 시각으로 바뀝니다.
- 이벤트 하나는 트랜잭션 하나로 커밋합니다. 그 트랜잭션에서 위의 반영, `event_sequence` 갱신, `event` 행 추가를 함께 합니다. 그래서 `message`, `part` 테이블의 행은 그 행을 마지막으로 바꾼 이벤트의 내용과 같습니다. 확인한 DB의 message 20개와 part 71개가 모두 그랬습니다.
- session을 지우면 child session을 먼저 지웁니다. 그다음 `session.deleted` 이벤트를 기록하고, 다른 트랜잭션에서 그 session의 `event`, `event_sequence` 행을 모두 지웁니다. 그래서 지운 session의 이벤트는 남지 않습니다.

### 한 대상의 여러 이벤트

`*.updated` 이벤트는 바뀐 뒤의 대상 전체를 담으므로, 같은 message나 part의 이벤트가 여러 번 기록되고 테이블에는 마지막 내용만 남습니다. 확인한 DB에서 대상마다 이벤트가 기록된 형태는 다음과 같습니다.

| 대상 | 이벤트 | 확인한 DB |
|---|---|---|
| user message | 만들 때 한 번 기록하고, 변경 요약(`summary.diffs`)을 갱신할 때마다 다시 기록합니다. | 응답이 없는 2개는 1번, 나머지 3개는 5~8번 |
| assistant message | 만들 때(`time.created`만), `finish`와 토큰을 채울 때, `time.completed`를 채울 때 | 15개 모두 3번 |
| user `text` part | `time` 없이 한 번 | 5개 |
| assistant `text`, `reasoning` part | 시작할 때(빈 `text`, `time.start`)와 끝날 때(전체 `text`, `time.end`) | 15개 모두 2번 |
| `tool` part | `pending`, `running`(한 번 이상), `completed` 또는 `error` | 20개는 3번, `bash` 1개는 `running` 3번을 포함해 5번 |
| `step-start`, `step-finish` part | 한 번 | 각각 15개 |

끝난 part가 나중에 다시 기록되기도 합니다.

- compaction이 `compaction` part에 `tail_start_id`를 채울 때
- prune이 오래된 `tool` part에 `state.time.compacted`를 채울 때([Compaction](#compaction) 참고)

## 동작별 기록 순서

### 사용자 입력

1. 새 session이면 `session.created`를 기록합니다.
2. 입력에 쓴 agent나 model이 session의 것과 다르면 `session.updated`로 바꿉니다.
3. user message의 `message.updated`를 기록하고, 이어서 part마다 `message.part.updated`를 한 번씩 기록합니다.
4. `session.updated`로 session의 `time.updated`를 바꿉니다.

첨부한 파일은 `file` part와 함께, OpenCode가 그 파일을 읽은 결과를 synthetic `text` part(`Called the Read tool with the following input: …`와 파일 내용)로 기록합니다. `@이름`으로 부른 agent는 `agent` part와, 그 agent를 `task` tool로 부르라는 synthetic `text` part로 기록합니다.

### 에이전트 루프

user message를 기록하면 OpenCode는 다음을 되풀이합니다. 한 번 되풀이할 때 LLM을 한 번 부릅니다.

1. `message.updated`: assistant message를 만듭니다. `time.created`만 있고 `tokens`는 0이며 `finish`가 없습니다.
2. `message.part.updated`: 응답 스트림이 시작되면 `step-start`를 기록합니다.
3. `message.part.updated`: 스트림이 오는 대로 `reasoning`, `text`, `tool` part를 기록합니다. 글은 시작과 끝에만 기록하며, 그 사이에 늘어나는 글은 기록하지 않습니다.
4. `message.part.updated`: 응답이 끝나면 `step-finish`를 기록합니다.
5. `message.updated`: `finish`, `tokens`, `cost`를 채운 assistant message를 기록합니다.
6. `message.part.updated`: 작업 디렉터리의 파일이 바뀌었으면 `patch`를 기록합니다.
7. `message.updated`: `time.completed`를 채운 assistant message를 기록합니다.

`finish`가 `tool-calls`이거나 assistant message에 tool part가 있으면 1부터 다시 되풀이하고, 그렇지 않으면 루프를 끝냅니다. assistant message에 `error`가 채워졌거나 사용자가 권한 요청을 거절했을 때도 루프를 멈춥니다(설정 `experimental.continue_loop_on_deny`가 `true`이면 거절해도 멈추지 않습니다). 설정의 권한 규칙으로 거부된 tool 호출은 `error` 상태로 끝나고 루프는 이어집니다.

루프와 따로 실행되는 다음 작업도 같은 session에 이벤트를 기록하므로, 그 이벤트가 루프의 이벤트 사이에 끼어듭니다.

- 제목: 첫 사용자 입력을 처리할 때 제목을 만드는 LLM 호출을 따로 하고, 그 결과를 `session.updated`로 기록합니다. child session은 제목을 만들지 않습니다.
- 변경 요약: 첫 LLM 호출 전과 step이 끝날 때마다 `session.updated`(`summary`)와 user message의 `message.updated`(`summary.diffs`)를 기록합니다. 1.19.5는 이때 session의 `summary`를 모두 0으로 기록하고, 바뀐 파일은 user message의 `summary.diffs`에만 기록합니다.

### tool 실행

- 모델이 tool 호출을 출력하기 시작하면 `pending`, 호출 인자를 다 받으면 `running`, 실행이 끝나면 `completed` 또는 `error`를 기록합니다.
- 실행 중에 tool이 진행 정보를 넘기면 `running`을 다시 기록합니다. 예를 들어 `bash`는 출력이 늘어날 때마다 `state.metadata.output`을 바꿔 기록합니다.
- 한 응답에서 tool을 여러 개 호출하면 tool이 함께 실행되고, 각 tool의 `completed`나 `error`는 끝난 순서대로 기록됩니다. 그래서 끝난 상태의 기록 순서는 호출 순서와 다를 수 있습니다([event 순서](#event-순서)의 seq 19~22).

### 중단

사용자가 응답 도중 중단하면 OpenCode는 다음을 기록하고 루프를 끝냅니다.

- 끝나지 않은 `text`, `reasoning` part: `time.end`를 채워 다시 기록합니다.
- 끝나지 않은 `tool` part: `error` 상태로 기록합니다. `error`는 `Tool execution aborted`이고 `metadata.interrupted`는 `true`입니다.
- assistant message: `error`(`MessageAbortedError`)와 `time.completed`를 채워 기록합니다.

OpenCode 프로세스가 강제로 종료되면 이 기록을 하지 못하므로, 끝 표시가 없는 part와 `time.completed`가 없는 assistant message가 남을 수 있습니다.

### Subagent

모델이 `task` tool을 호출하면 다음 순서로 기록합니다.

1. 부모 session: `task` tool part를 `pending`, `running`으로 기록합니다. `input`에는 `description`, `prompt`, `subagent_type` 등이 들어갑니다.
2. child session: `session.created`를 기록합니다. `info.parentID`는 부모 session의 id이고, `title`은 `<description> (@<agent 이름> subagent)`입니다.
3. 부모 session: `task` tool part를 `running`으로 다시 기록합니다. `title`은 `description`이고, `metadata`에 `parentSessionId`(부모 session id), `sessionId`(child session id), `model`이 들어갑니다.
4. child session: task의 `prompt`로 user message를 기록하고, [에이전트 루프](#에이전트-루프)대로 assistant message를 기록합니다.
5. 부모 session: child session의 루프가 끝나면 `task` tool part를 `completed`로 기록합니다. `output`은 child session의 마지막 `text` part의 글을 다음처럼 감싼 것입니다.

```
<task id="ses_…" state="completed">
<task_result>
…
</task_result>
</task>
```

- 부모 session과 child session은 aggregate가 달라 `seq`가 따로 늘어납니다. 두 session의 이벤트 순서는 `seq`로 비교할 수 없습니다.
- `task_id`로 이전 child session의 id를 넘기면 새 session을 만들지 않고 그 session에 이어서 기록합니다.
- 기본 설정(`subagent_depth` 1)에서는 child session에서 다시 Subagent를 띄울 수 없습니다.
- 사용자가 subtask로 설정한 command를 실행하면 user message에 `subtask` part를 기록합니다. 그다음 OpenCode가 LLM을 부르지 않고 assistant message와 `task` tool part(`running`부터)를 직접 기록하며, 2부터는 위와 같습니다.

### Compaction

compaction은 지금까지의 대화를 요약해 이후 LLM 호출의 입력을 줄이는 일입니다.

1. 사용자가 요청하면(`auto`: `false`), 또는 step이 끝났을 때 토큰이 모델의 context 한도에 가깝거나 요청이 한도를 넘어 실패하면(`auto`: `true`), 글이 없는 user message와 `compaction` part를 기록합니다.
2. 다음 반복에서 요약을 만드는 assistant message를 기록합니다. `agent`와 `mode`는 `compaction`, `summary`는 `true`, `parentID`는 1의 user message입니다. 요약은 이 message의 `text` part에 있으며, 이 호출에서는 tool을 쓰지 않습니다.
3. 요약하지 않고 남긴 최근 message가 있으면 그 첫 message의 id를 `compaction` part의 `tail_start_id`에 채워 다시 기록합니다.
4. 자동 compaction이면 user message를 하나 더 기록합니다. 요청이 한도를 넘어 실패했을 때(`overflow`: `true`)는 마지막 사용자 입력을 다시 기록하며, 첨부한 미디어는 `[Attached <mime>: <파일 이름>]` 글로 바꿉니다. 그 밖에는 `Continue if you have next steps, or stop and ask for clarification if you are unsure how to proceed.`라는 synthetic `text` part를 기록합니다.

compaction 이전의 message는 DB에 그대로 남지만 이후 LLM 호출의 입력에는 들어가지 않습니다. 입력은 compaction user message, 요약, 남긴 최근 message, 그 뒤의 message로 이루어집니다.

설정 `compaction.prune`이 `true`이면 루프가 끝난 뒤 최근 tool 출력을 일정량 남기고, 그보다 오래된 `completed` tool part에 `state.time.compacted`를 채워 다시 기록합니다(prune). 이 tool의 출력은 이후 LLM 호출의 입력에서 `[Old tool result content cleared]`로 바뀝니다.

### 되돌리기

1. 사용자가 되돌리면 되돌릴 위치를 session의 `revert`에 채워 `session.updated`로 기록합니다. 이때는 message를 지우지 않습니다.
2. 되돌리기를 취소하면 `revert`를 비워 `session.updated`로 기록합니다.
3. 되돌린 채로 새로 입력하면 되돌린 위치 뒤의 message와 part를 지우고(`message.removed`, `message.part.removed`), `revert`를 비운 뒤(`session.updated`) 새 입력을 기록합니다.

지운 message와 part의 앞선 이벤트는 `event` 테이블에 그대로 남습니다.

## DB만으로 알 수 없는 것

다음은 OpenCode가 실행 중에 쓰거나 만들지만 DB에 기록하지 않습니다.

- 스트리밍 중의 내용: 늘어나는 글은 `message.part.delta`로 알리기만 합니다. tool 호출 인자도 다 받은 뒤(`running`)에야 기록합니다.
- system prompt와 tool 정의: LLM을 부를 때마다 환경 정보, instruction 파일, MCP 안내, skill 목록 등으로 system prompt를 만들고 쓸 수 있는 tool을 정합니다. user message의 `system`, `tools`에는 입력할 때 따로 넘긴 값만 들어갑니다.
- LLM 입력으로 바꿀 때의 변경: message와 part를 LLM 입력으로 바꿀 때 다음처럼 바꾸며, 바꾼 결과는 기록하지 않습니다.
  - compaction 이전의 message를 뺍니다.
  - `compaction` part를 `What did we do so far?`로, `subtask` part를 `The following tool was executed by the user`로 바꿉니다.
  - prune한 tool 출력을 `[Old tool result content cleared]`로 바꿉니다.
  - `ignored`가 `true`인 user `text` part와, 오류로 끝난 assistant message를 뺍니다. 중단한 assistant message는 `step-start`, `reasoning` 밖의 part가 있으면 넣습니다.
  - agent에 최대 step 수가 정해져 있고 그 수에 이르면 마지막 호출에 안내 글을 덧붙입니다.
- reminder: plan agent를 쓰거나 plan agent에서 build agent로 돌아올 때의 안내 글은, 실험 기능 `OPENCODE_EXPERIMENTAL_PLAN_MODE`를 켜지 않으면 기록하지 않고 입력에만 덧붙입니다.
- 제목을 만드는 LLM 호출: 결과 제목만 `session.updated`로 남습니다. 이 호출의 입력, 출력, 토큰은 기록하지 않으며 session의 누적 토큰에도 들어가지 않습니다.
- compaction 요약 호출의 입력: 요약을 만드는 assistant message에는 출력(요약)만 남습니다. 요약 지시문과 펼친 대화로 이루어진 입력은 기록하지 않습니다.
- 공급자와 주고받은 원본: 원본 요청과 응답은 기록하지 않습니다. 공급자가 넘긴 일부 값(OpenAI의 `itemId` 등)만 part의 `metadata`에 남습니다.
