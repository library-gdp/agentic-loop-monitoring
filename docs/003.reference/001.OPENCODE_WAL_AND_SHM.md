# 001.OPENCODE_WAL_AND_SHM.md

이 문서는 OpenCode v1(1.19.x)이 Session Log를 기록하는 SQLite DB 옆에 생기는 `-wal` 파일과 `-shm` 파일이 무엇이고 어떻게 바뀌는지 설명합니다. [OpenCode v1 Plugin](../002.implementation/006.plugin/003.opencode/001.OVERVIEW.md)의 Trigger와 수집 방식이 이 동작에 기대고 있습니다.

## 확인한 범위

- OpenCode 설정: OpenCode 1.19.5 바이너리에 들어 있는 DB 연결 코드에서 확인했습니다.
- DB와 WAL 헤더: OpenCode 1.19.5가 Linux에서 기록한 DB에서 확인했습니다.
- SQLite의 동작: SQLite 공식 문서([Write-Ahead Logging](https://www.sqlite.org/wal.html), [WAL-mode File Format](https://www.sqlite.org/walformat.html), [Database File Format](https://www.sqlite.org/fileformat.html))를 따릅니다.

## 파일 구성

OpenCode의 DB 디렉터리(기본 `$XDG_DATA_HOME/opencode/`)에는 파일이 세 개 있습니다.

| 파일 | 내용 | 사라지는 때 |
|---|---|---|
| `opencode.db` | DB 본체입니다. checkpoint가 끝난 페이지가 들어 있습니다. | 사라지지 않습니다. |
| `opencode.db-wal` | WAL(Write-Ahead Log) 파일입니다. 커밋했지만 아직 DB 본체에 옮기지 않은 페이지가 들어 있습니다. | 마지막 연결이 정상적으로 닫힐 때 |
| `opencode.db-shm` | WAL index 파일입니다. WAL 안에서 페이지를 찾는 색인과 연결 사이의 잠금 정보가 들어 있습니다. | 마지막 연결이 정상적으로 닫힐 때 |

채널이나 `OPENCODE_DB`로 DB 파일 이름이 다르면 `-wal`, `-shm` 앞부분도 그 이름을 따릅니다.

## OpenCode의 SQLite 설정

OpenCode 1.19.5는 DB를 열 때 다음 PRAGMA를 실행합니다.

| PRAGMA | 값 | 뜻 |
|---|---|---|
| `journal_mode` | `WAL` | WAL 모드로 기록합니다. |
| `synchronous` | `NORMAL` | 커밋마다 fsync하지 않고 checkpoint 때 fsync합니다. 전원이 꺼지면 마지막 커밋 몇 개를 잃을 수 있지만 DB가 깨지지는 않습니다. |
| `busy_timeout` | `5000` | 잠금을 얻지 못하면 최대 5초 기다립니다. |
| `cache_size` | `-64000` | 연결마다 페이지 캐시를 약 64MB까지 씁니다. |
| `foreign_keys` | `ON` | 외래 키를 검사합니다. |

이어서 `PRAGMA wal_checkpoint(PASSIVE)`를 한 번 실행합니다. `wal_autocheckpoint`는 바꾸지 않으므로 SQLite 기본값(1000 페이지)을 씁니다. DB의 페이지 크기는 4096바이트이므로 WAL이 약 4MB를 넘으면 커밋 때 checkpoint가 실행됩니다.

WAL 모드는 DB 파일 헤더에 기록되므로(헤더 18, 19번째 바이트가 `2`) 다른 프로세스가 DB를 열어도 WAL 모드로 열립니다.

## WAL 파일

### 쓰기

WAL 모드에서는 커밋할 때 바뀐 페이지를 DB 본체에 쓰지 않고 `-wal` 파일 끝에 frame으로 덧붙입니다. frame 하나는 24바이트 헤더와 페이지 하나로 이루어집니다. 트랜잭션의 마지막 frame에는 커밋 표시가 있어, 커밋 표시가 붙은 frame까지가 커밋된 내용입니다.

그래서 커밋할 때마다 `-wal` 파일이 바뀝니다. OpenCode Plugin은 이 파일의 변경 알림을 새 레코드가 커밋되었다는 신호로 씁니다.

### 읽기

읽기 트랜잭션은 시작할 때 WAL에서 마지막으로 커밋된 frame의 위치(end mark)를 기억합니다. 페이지를 읽을 때는 end mark 이전의 WAL에서 그 페이지의 가장 최근 frame을 찾고, 없으면 DB 본체에서 읽습니다. 그 결과는 다음과 같습니다.

- 읽기 트랜잭션은 시작한 시점의 snapshot을 봅니다. 그 뒤의 커밋은 다음 읽기 트랜잭션에서 보입니다.
- 읽기와 쓰기는 서로 막지 않습니다. 쓰기는 한 번에 한 연결만 할 수 있습니다.
- 커밋 표시가 붙지 않은 frame은 읽지 않으므로 읽은 행은 항상 커밋이 끝난 완전한 행입니다.

### Checkpoint

checkpoint는 WAL의 frame을 DB 본체에 옮겨 쓰는 작업입니다.

- 기본으로 커밋한 연결이 WAL이 1000 페이지를 넘었을 때 `PASSIVE` checkpoint를 실행합니다.
- 읽기 트랜잭션이 아직 보고 있는 frame보다 뒤는 옮기지 않습니다. 그래서 오래 걸리는 읽기 트랜잭션은 checkpoint를 늦추고, 그동안 WAL은 계속 커집니다.
- 모든 frame을 옮긴 뒤 읽고 있는 연결이 없으면, 다음 쓰기는 WAL을 처음부터 다시 씁니다. 이때 파일 크기는 줄지 않습니다(`journal_size_limit`을 정하지 않은 경우).

### 생성과 삭제

- 첫 연결이 DB를 열고 접근할 때 `-wal` 파일이 없으면 만듭니다.
- 마지막 연결이 정상적으로 닫힐 때 checkpoint를 실행하고 `-wal` 파일을 지웁니다.
- 프로세스가 강제 종료되면 `-wal` 파일이 남습니다. 다음에 DB를 연 연결이 남은 WAL을 복구합니다.

OpenCode를 끄면 `-wal` 파일이 사라졌다가 다시 켜면 새로 생깁니다. 그래서 OpenCode Plugin은 `-wal` 파일에 직접 감시를 걸지 않고 DB 디렉터리를 감시합니다. OpenCode가 꺼져 있을 때 Plugin이 DB를 읽어도 Plugin의 연결이 `-wal` 파일을 만들 수 있습니다.

## SHM 파일

### 내용

`-shm` 파일은 같은 DB를 연 연결들이 `mmap`으로 함께 쓰는 공유 메모리(wal-index)입니다. 다음이 들어 있습니다.

| 내용 | 설명 |
|---|---|
| 헤더 | WAL에서 마지막으로 커밋된 frame 위치, checkpoint가 진행된 위치 등 |
| read mark | 읽기 트랜잭션마다 자신이 본 end mark를 기록하는 칸. checkpoint가 어디까지 옮겨도 되는지 판단하는 데 씁니다. |
| 잠금 영역 | 쓰기, checkpoint, 읽기 잠금에 쓰는 바이트 |
| 해시 테이블 | 페이지 번호로 WAL 안의 frame을 찾는 색인 |

파일은 32KB 단위로 커지며, WAL frame 약 4096개마다 32KB가 늘어납니다.

### 성질

- **읽기만 해도 바뀝니다.** 읽기 트랜잭션은 시작할 때 read mark를 기록하므로 SELECT만 해도 `-shm` 파일의 내용이 바뀝니다. 그래서 `-shm` 파일의 변경은 새 커밋이 있다는 신호가 아닙니다. OpenCode Plugin은 이 알림을 거릅니다.
- **영구적인 데이터가 아닙니다.** 내용은 언제나 `-wal` 파일에서 다시 만들 수 있습니다. 마지막 연결이 닫힐 때 지워지고, 다음에 DB를 연 연결이 WAL을 읽어 새로 만듭니다.
- **같은 컴퓨터에서만 함께 쓸 수 있습니다.** 공유 메모리로 쓰므로 네트워크 파일시스템 위의 DB는 여러 컴퓨터에서 함께 열 수 없습니다.

## 다른 프로세스에서 읽을 때

OpenCode가 쓰는 동안 다른 프로세스(OpenCode Plugin)가 같은 DB를 읽을 때의 동작입니다.

| 항목 | 동작 |
|---|---|
| 읽기 전용 연결 | `-wal`, `-shm` 파일이 있거나 디렉터리에 만들 권한이 있으면 읽기 전용으로 열 수 있습니다. 읽기 전용 연결도 `-shm` 파일에 read mark를 기록합니다. |
| OpenCode의 기록 | 읽기 트랜잭션이 OpenCode의 커밋을 막지 않습니다. |
| 일관성 | 읽기 트랜잭션 하나 안에서는 같은 snapshot을 봅니다. OpenCode는 `event`, `event_sequence`, `message`, `part`를 한 트랜잭션으로 커밋하므로 한 snapshot 안에서는 이 테이블들이 서로 맞습니다. |
| 긴 읽기 | checkpoint를 늦추어 WAL을 키웁니다. OpenCode Plugin은 `LIMIT`으로 나누어 읽어 읽기 트랜잭션을 짧게 유지합니다. |
| 파일 복사 | DB 본체만 복사하면 checkpoint되지 않은 커밋을 잃습니다. DB를 옮기거나 백업할 때는 SQLite의 백업 API나 `VACUUM INTO`를 쓰거나, 세 파일을 함께 복사합니다. |
