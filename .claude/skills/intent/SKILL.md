# Intent

개발자가 프로젝트의 의도를 오해하지 않도록, 목적과 기대 결과를 사용자와 함께 확인해 `intent/`에 INTENT 문서로 남깁니다. 기술 구현 방법이 아니라 **왜 만드는지와 무엇이 달라져야 하는지**를 기록합니다.

## 규칙

- 소스 코드를 바꾸지 않습니다. 기능 구현이나 리팩터링도 시작하지 않습니다.
- 사용자가 승인하기 전에는 파일을 저장하지 않습니다. 커밋은 사용자가 따로 요청할 때만 합니다.
- 한 번에 질문은 **최대 3개**만 합니다.
- 확인되지 않은 정보는 추측해서 채우지 않고 Open Questions에 기록합니다.
- 사용자가 "지금 정할 필요 없다"고 한 항목은 더 묻지 않고 Open Questions로 옮깁니다. "생각하지 말라"고 한 항목은 문서에서도 다루지 않습니다.

## 시작 모드

인자: `$ARGUMENTS`

- **인자가 없을 때 (아이디어 발전 모드)**: 사용자의 아이디어가 아직 다듬어지지 않았다고 가정합니다. 질의응답으로 아이디어를 발전시킵니다.
  - 첫 질문은 열린 질문으로 합니다. 예: 어떤 불편이나 계기에서 시작했는지, 누가 그 문제를 겪는지, 해결되면 무엇이 달라지는지
  - 답변을 받으면 문제 정의를 한 문장으로 다시 정리해 보여 주고, 맞는지 확인합니다.
  - 답변에 숨은 가정이 있으면 짚고, 범위를 좁히거나 넓히는 선택지를 제시합니다.
  - 아이디어가 프로젝트 전체의 의도인지, 특정 기능의 의도인지 확인합니다.
- **인자가 있을 때**: 인자를 문서의 주제나 범위로 받아들입니다. 인자와 저장소에서 이미 알 수 있는 내용은 다시 묻지 않고, 빈 부분만 인터뷰합니다.

## 절차

### 1. 저장소 분석

다음을 읽고 프로젝트의 목적과 현재 상태를 파악합니다.

- `README.md`, `AGENTS.md`, `CLAUDE.md`
- `AGENTS.md`의 문서 표에 있는 설계 문서와 ADR 가운데 주제와 관련된 것
- 소스 코드 (있다면 구조와 주요 진입점 정도)
- `intent/`의 기존 INTENT 문서(`INTENT-*.md`). 있으면 반드시 먼저 읽습니다. 문서의 버전은 파일명에서 확인합니다.

### 2. 파악 결과 공유

인터뷰 전에 다음을 짧게 정리해 보여 줍니다.

- 목적: 문서에서 읽은 프로젝트의 목적
- 현재 상태: 구현 정도, 설계에서 정한 것과 정하지 않은 것
- 기존 INTENT 문서의 유무와 버전. 이 버전이 현재 개발 중인 애플리케이션 버전입니다.
- 비어 있는 부분: 문서에 잘 드러나지 않아 인터뷰가 필요한 부분 (예: 누가, 무엇을 보고, 무엇을 판단하려는가)

### 3. 인터뷰

라운드마다 최대 3개의 질문을 합니다.

기존 INTENT 문서가 있으면 첫 라운드에서 이번 작업이 다음 중 무엇인지 확인합니다. 인자나 대화에서 이미 분명하면 묻지 않습니다.

- **현재 버전 보완**: 지금 개발 중인 버전의 의도를 다듬거나, Open Question을 해결합니다.
- **새 버전 개발**: 새 버전의 애플리케이션을 개발하기 위해 새 의도를 정합니다. [버전 규칙](#버전-규칙)에 따라 새 버전 번호도 정합니다.

- 질문에는 고를 수 있는 예시나 선택지를 붙입니다. 사용자가 자유롭게 답할 여지도 남깁니다.
- 각 라운드를 시작할 때 이전 답변을 정리해 보여 줍니다.
- 답변이 기존 설계와 충돌하거나 간격이 있으면 파일과 위치를 들어 짚고, 다음 질문에서 확인합니다. 해결 방법은 정하지 않고, 간격은 Open Questions에 기록합니다.
- 초안 전 마지막 라운드라면 그렇다고 알립니다.

다음 항목이 확인되거나 Open Questions로 넘어갈 때까지 인터뷰합니다.

- 범위: 프로젝트 전체인지, 특정 기능이나 마일스톤인지
- 문제: 지금 무엇이 어렵고, 누가 겪는지. 프로젝트에서 쓰는 핵심 개념(예: "실패")을 사용자가 어떻게 정의하는지
- 기대 결과: 사용자가 이 결과물로 무엇을 할 수 있게 되는지
- 범위 밖: 의도적으로 하지 않을 것
- 사용자와 대상 시스템: 누가 쓰고, 사용 범위를 어떻게 넓혀 가는지, 무엇과 상호작용하는지
- 제약: 반드시 지켜야 하는 조건

### 4. 초안 제시

[문서 구조](#문서-구조)에 따라 템플릿을 채워 초안을 작성해 대화에 보여 줍니다. 아직 파일로 저장하지 않습니다.

- 기존 INTENT 문서가 있으면 기존 문서와 초안의 차이를 diff로 보여 줍니다.
- 문서의 버전을 밝힙니다. 새 버전이면 그 번호를 정한 이유를 한 줄로 설명합니다.
- 사용자의 답변을 해석해서 쓴 표현과 정의하지 않고 둔 용어를 짚어 확인을 요청합니다.
- 저장할 경로를 제안합니다. 파일명은 항상 `INTENT-{version}.md`입니다(예: `INTENT-1.0.md`). 프로젝트 전체의 의도는 `intent/INTENT-{version}.md`에 둡니다. 특정 기능의 의도라면 `intent/` 아래에 둘 디렉터리를 사용자와 정합니다(예: `intent/<기능 이름>/INTENT-{version}.md`).

### 5. 저장

사용자가 승인하면 다음을 수행합니다.

1. 문서를 `INTENT-{version}.md`로 저장합니다. 새 버전 개발이면 `git mv`로 기존 파일명을 새 버전으로 바꾼 뒤 내용을 고칩니다. 이전 버전은 Git 이력으로 남기고, 같은 디렉터리에 여러 버전의 파일을 두지 않습니다.
2. `AGENTS.md`의 Intent 표에 행을 추가하거나 갱신합니다. 링크는 새 파일명을 가리켜야 하고, 요약은 문서의 Proposed Outcome을 한 문장으로 줄인 것입니다. Intent 섹션이 없으면 Documentation 섹션 앞에 다음 형식으로 만듭니다.

   ```markdown
   ## Intent
   프로젝트의 목적과 기대 결과는 `intent/`에서 관리합니다. 기능의 범위나 우선순위를 판단해야 할 때 먼저 읽으세요.

   | 문서 | 요약 |
   |---|---|
   | [INTENT-1.0.md](intent/INTENT-1.0.md) | <한 문장 요약> |
   ```

3. 파일명이 바뀌었다면 저장소에서 이전 파일명을 가리키는 링크를 찾아 함께 고칩니다.
4. 저장한 파일을 알리고, 커밋할지 묻습니다.

## 문서 구조

문서는 [assets/templates/intent.md](assets/templates/intent.md)를 따릅니다. `<...>`는 채울 내용에 대한 안내이므로 실제 내용으로 바꿉니다.

- 해당하는 내용이 없는 하위 섹션(범위 밖, 현재 설계의 원칙 등)은 생략합니다. 최상위 섹션은 생략하지 않습니다. 내용이 없으면 "없음"이라고 씁니다.
- 용어는 프로젝트의 Glossary를 따릅니다.
- 링크는 문서 위치를 기준으로 한 상대 경로로 씁니다. 예: `intent/`에서 `docs/`는 `../docs/`
- 문서는 사용자와 대화한 언어로 씁니다.

## 버전 규칙

INTENT 문서의 버전이 곧 애플리케이션의 버전입니다. 애플리케이션 버전이 INTENT 문서를 따라가므로, 버전을 다른 곳에서 찾지 않습니다. 버전은 파일명 `INTENT-{version}.md`에 명시합니다. 새 버전의 INTENT 문서를 작성한다는 것은 새 버전의 애플리케이션 개발을 시작한다는 뜻입니다.

| 상황 | 버전 | 처리 |
|---|---|---|
| 첫 문서 | `1.0`을 제안하고 사용자에게 확인합니다. | 파일을 만들고, Version History에 첫 행을 추가합니다. |
| 현재 버전 보완 | 그대로 | 파일명을 유지합니다. Version History의 마지막 행에 변경 내용을 보태고, Last Updated를 갱신합니다. |
| 새 버전 개발 | 사용자가 정합니다. | 파일명을 새 버전으로 바꾸고, Version History에 행을 추가하고, Last Updated를 갱신합니다. |

새 버전 번호는 `Major.Minor` 형식으로 제안하고 사용자의 확인을 받습니다. 기존 의도를 넓히는 버전이면 Minor를, Problem이나 주 사용자처럼 의도의 바탕이 바뀌는 버전이면 Major를 올리는 것을 제안합니다.

파일명의 버전과 Version History의 마지막 행은 항상 같아야 합니다.
